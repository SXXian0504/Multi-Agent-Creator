## 项目介绍

整个系统通过一个Orchestrator去统一编排各个Agent的执行流程，形成了一个“生成—评审—重新规划”的闭环。用户输入一个选题后，系统能够自动完成标题、大纲、正文以及配图生成，并且支持SSE流式输出，让用户实时看到当前生成进度。另外，在标题确认和大纲确认阶段，我还引入了Human-in-the-loop机制，允许用户在关键节点中途调整创作方向，再继续后续生成。

技术上主要使用了 Prompt 工程、RAG、Tool Calling、Skill等AI应用开发技术。其中一个比较核心的问题，是如何保证大模型输出的稳定性。因为实际开发过程中，我发现模型经常会出现Markdown包裹JSON、JSON不完整、字段缺失、枚举值非法等情况，这些问题会导致后续 Agent 无法继续执行。所以我专门封装了结构化输出服务，对模型结果进行JSON提取、括号平衡解析、类型校验以及业务规则校验，并结合失败重试机制，提升多阶段协作的稳定性和可控性。

在配图部分，我支持了多种图片来源和工具，包括图库检索、文生图、流程图等，并通过策略模式统一管理不同图片服务。同时为了保证系统可靠性，我还设计了多层降级机制。单张图片失败时会自动重试并重新规划；如果最终仍然失败，则会降级到兜底图片，避免整篇文章生成链路中断。

在工程化方面，我比较关注系统性能和用户体验。因为图片生成整体比较耗时，所以我结合线程池实现异步化处理，通过对正文生成和配图生成进行并行执行，将整体生成耗时降低了大约15秒。另外，我还通过AOP实现了Agent执行链路监控，自动记录耗时、异常信息等数据。

目前系统生成一篇5000字左右、带有5到6张配图的完整图文，大约会消耗13000 token，平均耗时在325秒左右。

## 多智能体

### 你这个项目到底是 Multi-Agent，还是普通 Workflow？

这个项目外层确实有 Workflow，但它不是一个固定 Pipeline，而是一个Agentic Workflow。我没有把它包装成完全自治 Agent。

这个项目的核心价值是把 Agent 能力工程化落地：用 Workflow 管住流程边界，用 Agent 处理生成、评审和规划这任务，再通过结构化输出、日志和评测保证系统可控。

我的设计思路是：确定性的流程控制交给 Workflow，比如阶段流转、任务落库、SSE 推送、最大重试次数、失败降级这些工程边界；不确定性的生成、规划和评审交给 Agent，比如文本生成、配图需求分析、图片工具选择、内容质量评审、失败后的重规划建议等。

项目中涉及ImageAgent会根据ArticleAgent生成的文本内容，规划配图，并在工具失败或评审不通过时进行单图重规划。ReviewAgent负责对内容、图文是否匹配去做评审，并且输出评分、问题、建议以及下一步动作。Workflow 再根据这些 Agent 输出决定继续执行、重试、重规划还是降级。

所以我不会把它包装成“全自治Agent系统”。更准确地说，它是Workflow管控下的Multi-Agent协作：Workflow保证流程稳定性、可观测性和可降级，Agent 负责大模型擅长的生成、评审和规划决策。这样既能保证工程可控，也保留了Agent自我决策的能力和灵活性。

### Agent 的自我决策体现在哪里？

主要体现在三个地方。
第一，ArticleAgent 根据主题、平台、风格、知识库上下文生成标题、大纲和正文。
第二，ImageAgent 根据文章语义分析配图需求，并选择合适的图片工具，比如文生图、Mermaid、Graphviz流程图、图库检索等。
第三，ReviewAgent 主要分成文本评审和配图评审，对标题、大纲、正文、做质量评审，输出评分、问题、建议和下一步动作。

特别是图片链路，如果工具失败或评审不通过，不是简单重复调用，而是把失败原因和评审意见交给 ImageAgent 重新规划。

### 什么不让 Agent 直接控制整个流程？

我的设计是 Agent 负责语义决策，Workflow 负责流程边界。将一些确定性的流程控制交给 Workflow，比如阶段流转、任务落库、SSE推送、最大重试次数、失败降级这些工程边界。这样既能保证工程可控，也保留了Agent自我决策的能力和灵活性。

### Agentic Workflow 具体怎么编排？

由Orchestrator编排主流程。前面阶段调用 ArticleAgent 生成标题和大纲，并由 ReviewAgent 评审；标题和大纲确认节点接入 Human-in-the-loop。正文阶段会并行执行正文生成和配图规划，配图分支由 ImageAgent 生成配图需求，再由图片工具执行服务调用具体工具，最后由 ReviewAgent 评审图片结果。

如果图片评审不通过，就把observation传回ImageAgent进行单图重规划；多次失败后走fallback。

### Agentic Workflow是怎么实现的，讲一下具体实现

Orchestrator 在我的项目里不是一个大模型 Agent，而是一个确定性的流程调度器。它的核心职责是按阶段调度 Agent、准备上下文、接收结果并写回共享状态、控制串行和并行关系，以及处理失败降级。

具体来说，标题阶段它调用 ArticleAgent 生成标题并写入 state.titleOptions；用户确认标题后，大纲阶段再调用 ArticleAgent 生成大纲并写入 state.outline；用户确认大纲后，正文阶段调用 ArticleAgent 生成正文，同时启动配图分支，由 ImageAgent 规划配图并交给图片执行服务生成图片。两个分支结束后，Orchestrator 把正文和图片结果合并到同一个 ArticleState，最后调用 ContentMergeService 做图文合成。

所以我调度 Agent 的方式不是让 Agent 互相直接调用，而是通过 Orchestrator 管流程，通过 ArticleState 传上下文。Agent 只负责生成、规划、评审这些语义任务，Orchestrator 负责决定执行顺序、等待用户确认、并行执行和失败降级。

------

Agent 负责生成、规划、评审这些不确定性任务，Orchestrator 负责阶段顺序、并行调度、结果合并和异常降级。

项目里的 Agentic Workflow 主要是通过 应用层任务控制 + Workflow 编排 + 共享状态 + Agent 决策 + Service 兜底执行 来实现的。

第一层是应用层任务控制。用户创建文章任务后，ArticleController 会先创建任务记录并返回 taskId，然后通过 ArticleGenerationApplicationService 异步执行生成流程。应用层负责维护任务生命周期，比如更新文章状态、阶段状态、保存中间结果、推送 SSE，以及在异常时统一切到失败状态。

第二层是 Workflow 编排。核心类是 OrchestratedArticleWorkflow，它负责按阶段调用不同 Agent。整体流程是：

ArticleAgent 生成标题
 -> ReviewAgent 评审标题
 -> 用户确认标题
 -> ArticleAgent 生成大纲
 -> ReviewAgent 评审大纲
 -> 用户确认大纲
 -> ArticleAgent 生成正文
 -> ImageAgent 规划配图
 -> 图片工具执行
 -> ReviewAgent 评审图片结果
 -> 失败则重规划 / 重试 / fallback
 -> ContentMergeService 图文合成

这里 Workflow 管的是顺序、状态、异常边界和 fallback，不把这些确定性流程交给模型自由决定。

第三层是共享状态。Agent 之间不是直接互相聊天，而是通过 ArticleState / ArticleContext 传递上下文。比如标题生成结果会写入 titleOptions，用户确认后写入 title；大纲写入 outline；正文写入 content；配图计划写入 imageRequirements；评审结果写入 ReviewResult。后续 Agent 读取这些结构化字段继续处理。

第四层是 Agent 决策。ArticleAgent 负责标题、大纲、正文生成；ImageAgent 根据文章语义决定配图位置、类型、工具和参数；ReviewAgent 负责对标题、大纲、正文、配图计划和图片结果做评分、指出问题，并输出下一步建议。所以 Agent 处理的是生成、规划、评审这些不确定性任务。

第五层是工程兜底。比如结构化输出由 JsonStructuredOutputService 做解析、业务校验、修复和重试；图片工具执行由工具层处理重试和 fallback；图文合成由 ContentMergeService 做确定性合成；SSE 由 ArticleGenerationEventPublisher 统一把内部事件转换成前端消息。

所以我理解的 Agentic Workflow 不是完全自治 Agent，而是 Workflow 控制工程边界，Agent 负责语义决策。这样既能保证系统可控，也能保留 Agent 在生成、评审和重规划上的灵活性。

### 接入了哪些大模型？怎么接入的

第一类是文本生成模型。标题生成、大纲生成、正文生成、配图规划和部分结构化输出，主要通过 Spring AI Alibaba 接入 DashScope 的通义千问模型。代码里注入的是 DashScopeChatModel。普通生成用call，如果是需要前端实时展示的长文本，会使用流式接口stream。

第二类是文本评审模型。ReviewAgent 的文本评审使用的是 qwen-max，主要评审标题、大纲、正文和配图计划。它会根据当前阶段内容、平台风格 Skill 和评审标准，输出结构化的评分、问题、建议和下一步动作。

第三类是多模态评审模型。图片结果评审使用的是 qwen-vl-plus。这里主要通过 DashScope 兼容 OpenAI 的 chat completions 接口接入，把图片 URL 和评审 Prompt 一起传给模型，让它判断图片和文章章节是否匹配。

第四类是 Embedding 模型。RAG 入库时使用 text-embedding-v4，通过 DashScope 兼容 OpenAI 的 embeddings 接口调用。请求里传入文档切片文本，返回 1536 维向量，再写入 PostgreSQL / PGVector，用于后续相似度检索。

第五类是文生图模型。项目里接入了阿里万相 wanx-v1，用于 AI 配图生成。它是异步任务模式，先提交 prompt、size、n 等参数拿到 taskId，然后轮询任务结果获取图片 URL。这里的URL通常是临时URL，所以还通过COS对象存储，保存为稳定的图片访问地址。

### 状态怎么切换

状态切换是事件驱动的。创项目里的流程状态切换主要由三类事件触发：接口请求、Agent / Workflow 阶段完成事件、异常事件。

建任务、确认标题、确认大纲这些用户接口会触发阶段推进；Workflow 内部通过 Agent 完成事件触发正文、配图、合成阶段的状态切换；异常则由应用层统一切到 FAILED。整个状态都持久化在 Article 的 phase 字段中，Agent 本身只产出结果，不直接决定状态切换。

### Agent之间如何进行上下文通信

项目里Agent之间的上下文通信主要通过共享状态对象完成。Workflow负责创建和维护状态，Agent从状态中读取自己需要的上下文，执行后把结构化结果写回状态，下一个Agent再基于这些结果继续处理。

### Human-in-the-loop 体现在哪里？

主要放在标题和大纲两个关键节点。标题会生成多个候选项，用户选择后再进入大纲生成；大纲生成后用户可以确认或修改，再进入正文生成。

这样做是因为标题和大纲对最终文章质量影响最大，完全自动生成容易偏离用户预期。

### “重规划”和“重试”有什么区别？

重试是用相同参数再次执行，比如图片工具偶发失败后重试一次。

重规划是根据失败原因重新生成方案，比如原来用图库检索得到的图片和章节不匹配，ReviewAgent会给出问题和建议，ImageAgent可以改用文生图或者Mermaid、Graphviz流程图，并重新生成调用工具prompt或关键词。

所以重规划比重试更Agentic，它是基于反馈的再决策。

### 这三个 Agent 的边界怎么划分？

ArticleAgent 只负责文本创作，包括标题、大纲、正文。
ImageAgent 只负责配图规划和失败后的重规划，不直接执行图片工具。
ReviewAgent 只负责质量评审，包括文本质量、配图计划合理性和图片结果匹配度。

图片工具调用、JSON 解析、图文合成这些确定性逻辑放在 Service 层，不放在 Agent 里。

### reviewAgent输出的回答也有可能不符合用户要求吧，你怎么证明reviewAgent有效

ReviewAgent本身也是大模型，所以我不会假设它一定正确。我的做法是把它当成一个“可约束、可观测、可评测”的质量评审组件，而不是绝对裁判。

首先，会给ReviewAgent提供不同阶段的评审标准。
Prompt会注入当前平台、文章风格、阶段目标和评审维度。比如标题评审的维度侧重在相关性和吸引力，大纲阶段关注结构完整性，正文阶段关注信息密度、逻辑和风格一致性，配图阶段关注图文匹配度。

其次，ReviewAgent也遵循结构化输出，系统会校验ReviewAgent的回答是否可用。字段包括是否通过（approved）、得分（score）、存在的问题（problems）、建议（suggestions）、下一步动作（nextAction）。分数必须在 0-100，文本评审要包含维度分数，problems、suggestions、nextAction 不能为空。也就是说，ReviewAgent 至少要给出可执行的判断依据，而不是随便返回一段评价。

最后，通过离线评测验证它是否有帮助。用20个固定主题集对原来和完整闭环流程进行对比，统计任务成功率、各阶段成功率、结构化输出成功率、图片工具成功率、fallback、重规划次数、消耗token数、耗时等指标。
引入ReviewAgent后，从评分和重规划次数来看，存在低质量结果触发重规划的情况，并且重规划后，配图与文本内容更匹配，得分上涨，就说明它对结果的质量提升有实际帮助。

当然，ReviewAgent不能证明每一次判断都符合用户主观偏好，所以关键节点仍然保留Human-in-the-loop，比如标题和大纲由用户确认。它更多解决的是基础质量、结构完整性、图文匹配去进行评审，最终偏好仍然交给用户确认和反馈闭环。

### ReviewAgent一直不通过怎么办？

如果 ReviewAgent 一直不通过，系统不会无限重试。我在 Workflow 和执行服务里设置了最大重试 / 重规划次数，超过次数后会走降级策略，保证主流程可以结束。

文本链路里我不会让 ReviewAgent 无限否决，通常只做一次基于建议的重写。标题和大纲属于关键节点，不通过会让任务停在当前阶段或交给用户调整；正文为了保证可交付性，会保留较优结果并继续后续流程，同时记录评审意见。

ImageAgent 生成配图计划后，ReviewAgent 会评审计划是否合理。
如果不通过，会带着评审建议重新生成一次配图计划。
如果仍不通过，就抛出 ReviewRejectedException，Workflow进入失败处理或降级路径。

图片结果评审不通过时，不是让整个任务失败，而是进入单图重规划：图片结果不通过，会先构造observation结构化反馈对象，里面包含原始配图需求、工具错误、生成结果、评审问题、修改建议和尝试次数。它会传给 ImageAgent，让 ImageAgent 基于具体失败原因重新选择工具或改写 prompt / keywords。接着执行工具，重新进行评审。

但这里也有最大次数，比如当前代码里单图最多重规划 2 次，超过后会从历史候选图中选评分最高的一张作为结果。如果完全没有可用图，则使用fallback图片，不会阻塞整篇文章生成。

### observation是什么，怎么构造，起什么作用

observation是图片执行失败或评审不通过后的结构化反馈对象，里面包含原始配图需求、工具错误、生成结果、评审问题、修改建议和尝试次数。它会传给 ImageAgent，让 ImageAgent 基于具体失败原因重新选择工具或改写 prompt / keywords。这样重规划不是简单重试，而是基于反馈的Agent决策。

### 怎么做失败处理和降级路径

失败通常分为配图计划阶段失败和单张图片执行阶段失败，对应的处理策略也不一样。

配图计划是整体级别的输入，如果计划连续不通过，说明 Agent 对文章配图策略没有形成可执行方案，继续调用工具意义不大，所以当前实现选择中断或后续扩展为纯文本降级。

而对于执行级失败，可以认为是局部失败，可能只是某个工具不可用、关键词不准或图片匹配度不够，所以可以通过重试、重规划保证整篇文章继续完成。通常先工具重试，再根据错误或评审结果调用 ImageAgent进行单图重规划，超过最大次数后选择最高分候选图或 fallback图片，避免局部配图失败阻塞整篇文章。


## 结构化输出

### 结构化输出的三层治理

为了让Agent之间的数据传递从自然语言变成结构化对象，系统采用了json。

在结构化输出方面，没有只停留在Prompt层，而是做了分层治理的机制。主要分成Prompt约束层、统一解析和业务校验层、重试和可观测层。
第一层：首先最基础是设计结构化prompt，要求模型按照json格式输出。比如确定标题阶段大模型应该返回mainTitle和subTitle字段等等。

但是实际应用中，只靠prompt控制大模型输出是不可靠的，有可能会返回markdown代码块，在json前后加了解释的文字，有可能存在字段缺失、枚举值错误等等。因此需要进一步对大模型返回的json字段做解析校验的处理。

第二层治理是应用层封装了一个负责统一解析校验的json结构化输出服务。Agent拿到大模型回答后先调用服务解析，通过括号平衡，从原始文本中提取json。然后，根据当前输出类型做根类型校验，根类型通过后，再利用Gson工具类反序列化成对应的业务DTO。反序列化之后会做业务校验，比如枚举类是否合法，是否有必填字段为空等等。把格式错误、字段缺失、业务不合法提前拦截，避免错误数据继续进入工具调用、图片生成或图文合成环节。

第三层治理是重试和可观测。当解析或业务校验失败时，可以重新调用一次 LLM，让模型重新生成结构化结果。同时每次解析都会记录指标，包括是否解析成功、重试次数、错误信息等，这些记录也会被写入日志监控当中，后续测评也能够统计JSON首次解析的成功功率、重试次数等。

###  JSON 解析和业务校验流程

首先，模型输出可能不是纯 JSON，可能会带 Markdown 代码块或者前后解释文本，所以我会先从原始输出中提取 JSON，支持去掉 ```json 代码块，也支持通过括号平衡提取完整的 {...} 或 [...]。

然后，根据当前输出类型做根类型校验。比如标题候选必须是数组，大纲、配图计划、评审结果必须是对象。根类型通过后，再反序列化成对应的业务 DTO。

反序列化之后还会做业务校验。比如标题数量必须是 3 到 5 个，主标题不能为空且不能超过 30 字；大纲章节编号必须连续；配图计划里的 imageSource 必须是合法枚举，AI 生图必须有 prompt，搜索类图片必须有 keywords；评审结果的分数必须在 0 到 100，并且要有问题、建议和下一步动作。

如果解析或业务校验失败，系统会记录 parseSuccess、businessValid、repairCount、retryCount 等指标，并通过 retrySupplier 重新调用一次模型。重试后仍失败，就抛出结构化输出异常，避免不可用的数据继续进入后续 Workflow。

所以这块的核心目标是把大模型的不稳定自然语言输出，转成后续 Agent Workflow 可以稳定消费的业务对象。

### 离线评测是怎么做的

我在项目里做了一个离线 AgentEval 机制，用来评估 Agent 链路的稳定性和优化效果。是用20个固定主题集批量跑生成流程。每个主题分别跑一遍baseline和experiment。baseline对应原来的基础生成链路，experiment对应当前的Agentic Workflow链路。

每次运行都会生成一个独立的 taskId，并记录这次任务的 ArticleState、Agent执行日志、图片执行trace、开始结束时间和最终文章产物。ArticleState里能拿到标题、大纲、正文、配图计划、图片结果以及ReviewAgent的评分；AgentLog里能拿到每个阶段的执行状态、耗时和结构化输出指标；图片trace里能拿到工具调用是否成功、是否fallback、是否发生重规划等信息。

最后由 AgentEvalAggregator 聚合这些记录，计算任务成功率、阶段成功率、JSON 首次解析成功率、结构化校验通过率、平均修复和重试次数、阶段耗时、P95总耗时、图片工具成功率、fallback 率、平均重规划次数，以及各阶段 ReviewAgent 评分。然后 AgentEvalReportGenerator会生成Markdown报告，用于对比 baseline 和 experiment 的差异。

所以我这个评测的重点不是证明某一篇文章主观上一定最好，而是把 Agent Workflow的稳定性、结构化输出质量、图片工具链路和失败降级情况量化出来，方便后续根据失败样例、耗时和重试数据继续优化 Prompt、工具策略和流程边界。

## RAG

### RAG的实现

项目里的 RAG 主要是面向用户个人知识库做的，不是一个公共知识库。它的目标是让用户上传自己的资料，比如写作素材、行业资料、历史文章或者个人表达风格，然后在生成标题、大纲和正文时按需注入相关上下文，提升内容的事实一致性、案例相关性和个性化表达。

实现上我把 RAG 拆成了三个部分：知识入库、生成时检索和上下文拼装。

第一部分是知识入库。用户创建知识库并上传文档后，系统会先保存文档元信息，然后进入 ingestion 流程。这里主要包括文档解析、文本切片、Embedding 生成和向量写入。文档解析会根据文件类型提取文本；切片由 DocumentChunker 完成，把长文档切成适合检索的 chunk；然后通过 RagEmbeddingService 调用 embedding 模型生成向量；最后由 PgVectorKnowledgeRepository 写入 PostgreSQL 的 pgvector 表中，同时记录 chunk 所属知识库、文档和用户信息。

第二部分是生成时检索。用户创建文章任务时可以选择是否开启知识增强，以及选择哪些个人知识库。生成阶段不是无脑检索，而是先由 RagService.buildRetrievedContext(article) 构建检索上下文。它会先判断用户是否开启了 knowledgeEnhanced，再解析用户选择的知识库 ID，查询当前用户可用的知识库。然后通过 RetrievalDecisionService 根据文章主题、平台、风格、用户补充描述和知识库信息判断是否需要检索，以及检索哪些知识库。

第三部分是向量检索和上下文拼装。如果决策结果是需要检索，就由 KnowledgeRetriever 根据决策结果到 pgvector 中做相似度检索，取回相关的 KnowledgeChunk。然后 RagContextBuilder 会把这些 chunk 整理成一段可注入 Prompt 的 retrievedContext。这个上下文会写入 ArticleState，后续 ArticleAgent 在生成标题、大纲和正文时都会读取并拼进 Prompt。

比如生成 Prompt 里会强调：参考用户知识库资料，但不要逐字照抄，也不要编造资料里不存在的数据。这样可以让模型利用资料中的事实、案例和表达风格，但不直接复制原文。

另外我做了降级处理。RAG 失败不会中断文章生成。如果知识库不可用、检索异常或者上下文构建失败，RagService 会捕获异常并返回空字符串，系统自动降级成普通创作流程。这样 RAG 是增强能力，不是主链路的单点故障。

## Skill

### Skill在项目中是怎么使用和实现的

把这些规则抽象成配置化 Skill，让同一套 Agent 可以根据用户选择的平台和风格动态生成不同的写作约束。

配置文件，里面分两类：
平台 Skill，比如默认、公众号、小红书、微博
内容风格 Skill，比如科技、营销、情感、教育、幽默

每个 Skill 配置里包含：
promptInstruction：生成阶段注入的写作要求
reviewRubric：ReviewAgent评审标准
imageGuidance：配图规划建议
wordRangeGuidance：不同字数范围下的篇幅建议
constraints：硬约束，比如不要编造事实、不要标题党

项目里的 Skill 本质上是写作策略配置层。我把平台规则、内容风格、篇幅建议、配图建议和评审标准抽象到 JSON 配置中，通过 SkillService 在运行时解析并注入到 ArticleAgent、ImageAgent 和 ReviewAgent。这样 Agent 不需要硬编码不同平台和风格的规则，既方便扩展，也能保证文本生成、配图规划和质量评审使用同一套风格约束。

### 什么是配置化Skill

配置化 Skill 是我对写作策略的抽象。它把不同平台、写作风格、篇幅要求和评审标准沉淀到 JSON 配置中，运行时根据用户选择动态组合并注入各个Agent Prompt中。这样新增平台或风格时主要改配置，不需要改Agent主流程，也能保证生成、配图和评审使用同一套风格约束。

### 为什么要用SKill，不直接写在Prompt里。优势是什么？

直接写在 Prompt 里当然可以，项目早期也可以这样做。但当平台、风格和阶段变多以后，硬编码 Prompt 会很难维护，所以我把这些可复用的写作策略抽象成 Skill 配置。

具体的优势可以为分三点。

第一是可以避免 Prompt 膨胀和重复。如果都直接写 Prompt，就会在多个 Prompt 里重复维护同一套规则。Skill 把这些规则集中到配置里，Agent 只负责引用。

第二，可以保证多阶段风格一致。内容生成不是只有一个 Prompt，而是多阶段的。Skill的作用是让这些阶段共享同一套平台、风格、字数和评审约束，保证前后输出一致。同时，reviewAgent也能够使用同一套标准去进行评审。

第三，方便扩展平台和风格。如果后续要增加其他平台或者其他写作风格，直接硬编码 Prompt 就需要改代码、重新发布。现在 Skill 是 JSON 配置，新增平台或风格主要加一段配置，包括：生成要求、评审标准、字数建议、约束条件。主流程和Agent代码基本不需要动。


## 配图

### ImageAgent怎么进行配图规划的

ImageAgent 的配图规划本质上是把文章语义转成结构化图片需求。它根据主题、标题、大纲/正文、平台风格、字数范围和可用工具，决定配图数量、位置、类型、工具、关键词和 prompt。生成后会经过结构化校验、工具白名单过滤和 ReviewAgent 评审；如果评审不通过，再根据评审建议重新规划。这样配图不是固定规则，也不是盲目文生图，而是基于内容语义和平台风格做工具级规划。

### 配图策略模式

配图工具执行层用了策略模式。我定义了统一的 ImageSearchService 接口，不同图片来源各自实现这个接口，比如 Pexels、国内图片检索、Qwen 文生图、Mermaid、Graphviz、Iconify。启动时 ImageServiceStrategy 自动注入所有实现，并按 ImageMethodEnum 注册到 Map。运行时 ImageAgent 只需要输出 imageSource，执行层就能根据这个枚举找到对应策略并执行。如果策略不可用、结果无效或上传失败，会统一走fallback。这样新增一种配图工具时，只需要新增一个实现类和枚举，不需要改主流程。

### Agent进行工具调用

在配图链路里，我把图片工具注册为 Agent 可调用的 Tool。ImageAgent 在拿到文章标题、大纲、写作风格后，会先分析每个位置是否需要配图，然后自主选择合适的工具，比如图库检索、文生图、Mermaid、Graphviz 等，并生成对应的关键词、prompt 或图表代码。

工具调用完成后，工具执行结果会返回给 ImageAgent 的上下文，里面包括图片 URL、使用的方法、position、是否成功以及错误信息。如果工具调用失败，ImageAgent 会根据错误原因重新选择工具或改写参数，比如 Mermaid 渲染失败时改用 Graphviz，图库检索不匹配时改用文生图或流程图。

但 ImageAgent 不负责最终质量裁判。工具只返回“有没有生成成功”，不代表图片一定适合文章。所以生成结果还会交给 ReviewAgent 做质量评审，ReviewAgent 会判断图文匹配度、章节相关性、可读性和是否需要替换，并输出评分、问题、建议和 nextAction。

如果 ReviewAgent 不通过，它会形成 observation 返回给 ImageAgent，ImageAgent 再基于这个反馈重新规划工具和参数。比如 ReviewAgent 判断“图库图片只是普通办公场景，无法表达系统架构关系”，ImageAgent 就可以把工具从图库检索切换为 Mermaid 或 Graphviz，并重新生成流程图 prompt。

所以这里的决策分两层：ImageAgent 负责工具选择、参数生成和失败后的重规划；ReviewAgent 负责结果质量评审。Workflow 只控制最大重试次数、状态流转和 fallback，避免 Agent 无限调用工具。

### Agent进行工具调度的情况，具体的调度的实现是怎么样的，通过什么函数方法

具体实现上，我会把图片生成能力封装成 ImageGenerationTool.generateImage(...)，用 Spring AI 的 @Tool 和 @ToolParam 暴露给模型。然后在 ImageAgent 调用大模型时，使用 ChatClient.prompt().tools(imageGenerationTool).call().content()，把工具绑定到本次模型调用上下文中。

这样模型在推理过程中可以主动发起 generateImage 的 tool call，并自动填充 imageSource、keywords、prompt、position 等参数。Spring AI 会拦截 tool call，反射调用对应 Java 方法，并把工具返回的 JSON result 放回模型上下文。ImageAgent 再根据 result 判断工具是否成功，失败时换工具或改写参数；成功后把图片结果交给 ReviewAgent 做图文匹配评审。

### 配图方式能不能全部使用文生图

我没有把所有配图都交给文生图，是因为不同内容适合不同工具。文生图适合封面、抽象概念、创意插画，但不一定适合所有场景。比如技术流程、系统架构、步骤关系，用Mermaid或Graphviz更准确；真实场景、人群、办公、生活类内容，用图库检索更快、成本更低，也更稳定。

所以我的设计不是固定使用某一种工具，而是让ImageAgent根据文章语义、章节类型和配图目标选择工具。如果最后生成的配图和文本内容不匹配，再由ReviewAgent给出反馈，ImageAgent重规划为更合适的工具。

### 配图正确率怎么评估

用 ReviewAgent 对配图计划和图片结果评分，并在 AgentEval 中统计图片工具成功率、图片评审通过率、fallback 率、重规划次数等指标。当前离线评测里图片工具成功率是 92.21%。

### 图库数据源、输出内容、检索口令是什么

图库来源包括 Pexels 和国内图片检索。输入是 ImageAgent 生成的 keywords，通常结合文章主题、章节标题、实体词和场景词；输出是图片 URL 或图片数据，系统会统一上传到 COS，最终返回可访问的图片 URL、position、method 等结果。

###  Tool Calling 怎么实现

如果按 Agent Tool Calling 讲，就是把图片能力封装成 @Tool 方法，如 generateImage，ImageAgent 调模型时通过 ChatClient.prompt().tools(imageGenerationTool).call() 绑定工具，模型在推理中发起 tool call，Spring AI 调用 Java 方法并把结果返回模型上下文。

### 结构化输出除了应用层补丁，还有什么前置操作

最基础是在Prompt层面明确只输出 JSON、给固定结构模板、限制枚举值、按阶段拆分任务、控制 RAG 上下文长度、降低 temperature、提供 few-shot 示例、收窄角色边界。后续如果有足够样本，也可以做 SFT 提升格式遵循能力。

### ReviewAgent 怎么判断一致性

它会结合当前平台和风格 Skill 的评审标准、文章标题/大纲/正文、配图计划或图片结果做评审。输出包括 score、approved、problems、suggestions、nextAction。Skill 提供风格和平台口径，ReviewAgent 负责按这个口径判断一致性。

## 异步

### 异步处理细节

异步主要用于长任务解耦，创建文章任务后，接口不会等标题、大纲、正文全部生成完才返回，而是在创建任务后立即返回 taskId，后台线程池继续异步执行生成流程，前端通过 SSE 监听进度。

具体实现是用户发起创作请求后，Controller只做参数校验、创建数据库记录、生成taskId:然后马上返回。真正耗时的创作逻辑放在 ArticleAsyncService 里，用@Async("articleExecutor")标注，Spring会把它丢到专门的线程池里去跑。前端拿到taskId后建立SSE连接，后台创作到哪一步就推到哪一步。

为什么要自定义线程池而不用Spring默认的?因为默认的SimpleAsyncTaskExecutor每次都创建新线程，没有线程复用，也没有任务队列的限制，在高并发场景下可能把系统资源耗尽。

我在AsyncConfig里配了一个ThreadPoolTaskExecutor:核心线程5个，最大线程10个，队列容量100。核心线程5个意味着同时能处理5个创作任务，由于AI调用是I/O密集型(大部分时间在等大模型响应)，线程并不会占用太多CPU。队列容量100保证了突发流量时任务不会被直接拒绝。拒绝策略选的是callerRunsPolicy，队列也满了的话就让调用方自己执行，这是一种比较稳妥的兜底方案。

### CallerRunsPolicy

是线程池的一种拒绝策略，当线程池和队列都满了，新的任务不会被丢弃，也不会抛异常，而是由提交任务的线程自己执行这个任务。

我在线程池里使用 CallerRunsPolicy，主要是为了避免任务在高并发下被直接丢弃。当线程池和队列都满了，任务会退回到提交线程执行，这样可以保证任务不丢，同时让调用方变慢，形成一种反压机制，避免系统继续无限接收生成任务。

## 后训练八股

### RLHF

RLHF 是基于人类反馈的强化学习，主要目的是让大模型不只是会预测下一个词，而是更符合人类对“好回答”的偏好。

它通常分三步。第一步是监督微调，用高质量的指令问答数据让模型先学会基本的指令跟随能力。第二步是训练奖励模型，也就是对同一个问题让模型生成多个回答，再由人工标注哪个回答更好，用这些偏好数据训练一个模型来给回答打分。第三步是强化学习优化，让模型继续生成回答，奖励模型负责打分，高分回答会被鼓励，低分回答会被抑制，常见方法比如 PPO。

所以 RLHF 的核心不是简单让模型背答案，而是把人类对回答质量的偏好转成奖励信号，让模型学会生成更有帮助、更安全、更符合人类预期的内容。不过它也有风险，比如奖励函数或奖励模型设计不好时，模型可能出现 reward hacking，也就是为了拿高分而钻奖励规则的空子，所以训练时还需要人工抽检、验证集评估和多维度指标监控。

### SFT

SFT 是监督微调，主要作用是让预训练模型学习高质量的人类示范回答。它使用成对的指令和标准答案继续训练模型，让模型学会按照指令完成任务，比如问答、摘要、代码生成、结构化输出等。

和预训练相比，SFT 更关注“怎么回答用户问题”；和 RLHF 相比，SFT 是直接模仿标准答案，而 RLHF 是通过人类偏好或奖励信号进一步优化回答质量。


### SFT步骤

SFT 是监督微调，让模型模仿高质量示范答案，提升指令跟随和领域任务能力。

准备数据
收集高质量的指令和答案数据，比如问答、摘要、代码、工具调用、结构化输出等。

清洗数据
去掉重复、错误、低质量、格式混乱、有安全风险的数据。

构造训练样本
把数据整理成模型能训练的格式。

用监督学习训练模型
让模型在看到用户指令后，尽量拟合标准答案，也就是模仿高质量回答。

验证和评估
在验证集上看回答质量、格式遵循、任务准确率、幻觉率等指标，避免过拟合。

### RLHF的步骤

RLHF 是基于人类反馈的强化学习，先让模型会回答，再用人类偏好训练奖励模型，最后用奖励信号进一步优化模型行为。

先做 SFT
先用高质量指令数据训练一个能正常回答问题的基础模型。

收集偏好数据
对同一个问题，让模型生成多个回答，由人工标注哪个回答更好。比如：

问题：解释 RAG
回答 A：更清楚、更准确
回答 B：啰嗦、有错误
人工标注：A 优于 B
训练奖励模型
用这些偏好数据训练一个奖励模型，让它学会给回答打分。

强化学习优化模型
让模型继续生成回答，奖励模型给回答打分。高分回答被鼓励，低分回答被抑制。常见算法是 PPO，也可以有 GRPO 等变体。

评估和安全检查
检查模型是否真的变好，比如 helpfulness、安全性、事实性、拒答率、reward hacking 等。

### PPO 和 DPO

PPO 可以理解成一种“边试边学”的强化学习方法。

模型先生成回答，然后用reward model给这个回答打分。回答得分高，就鼓励模型以后多生成类似回答；得分低，就降低这类回答的概率。

但如果模型一次更新太猛，可能会把原来的语言能力破坏掉。所以 PPO 会限制每次更新的幅度，让模型一点点往高分方向优化，而不是突然大幅改变。

它通常需要几部分：

当前要训练的模型 policy model
一个参考模型reference model，用来防止模型跑偏
一个奖励模型reward model，用来给回答打分
一个价值模型value model，用来估计当前模型在某个输入下的预期奖励，作为基准来计算 advantage，帮助判断一个回答到底是“真的好”，还是只是分数看起来高。

DPO 可以理解成一种“直接学偏好”的方法。

它不需要先训练reward model，也不需要让模型一边生成一边试错。它直接使用成对的偏好数据，比如同一个问题下：

比如同一个 prompt 下 ,给出一个好的回答和一个差的回答。
训练目标就是让模型以后更倾向于生成好的回答回答，减少生成另一种回答的概率。

所以 DPO 比 PPO 更简单，训练也更稳定，成本更低。

### GRPO 数学原理

PPO 通常需要额外训练一个价值模型，用它来估计每个回答的优势，也就是判断这个回答比模型当前平均水平好多少。GRPO 的思路是不再单独训练价值模型，而是用同一个问题下多条回答之间的相对好坏来估计优势。

具体来说，对于同一个 prompt，模型一次采样出多条回答，比如 4 条或 8 条。然后奖励函数会分别给这些回答打分，得到一组奖励值。GRPO 会计算这一组奖励的平均值和标准差，再看每条回答相对于组内平均水平是更好还是更差。

如果某条回答的奖励高于这一组的平均值，它的优势就是正的，训练时会提高模型生成这类回答的概率；如果某条回答低于平均值，它的优势就是负的，训练时会降低模型生成这类回答的概率。

### GRPO PPO

PPO 和 GRPO 都是用来做大模型强化学习优化的方法，目标都是让模型更倾向于生成高奖励回答，同时避免模型更新太猛、能力跑偏。

PPO 是“奖励模型打分 + 价值模型估计优势 + 限制更新幅度”；GRPO 是“同题多答案打分 + 组内相对比较估计优势 + KL 约束防止跑偏”。

PPO 可以理解成比较经典的 RLHF 方法。它会让模型生成回答，然后用奖励模型打分，再通过强化学习更新模型。PPO 里通常需要一个 价值模型 来估计每个回答的优势，也就是判断这个回答比模型当前平均水平好多少。同时 PPO 会用裁剪机制限制每次更新幅度，避免模型一下子偏离原来的分布太远。

GRPO 可以理解成 PPO 的一种简化变体。它不再单独训练价值模型，而是对同一个问题采样多条回答，然后比较这些回答在组内的相对好坏。比如同一个 prompt 生成 8 个回答，每个回答都有一个奖励分数。GRPO 会看某个回答是高于组内平均分还是低于组内平均分，高于平均分就增加它的生成概率，低于平均分就降低它的生成概率。

所以两者最大的区别是：

PPO 需要价值模型来估计优势，GRPO 用同一个问题下多条回答的组内相对奖励来估计优势，因此省掉了价值模型。

GRPO 的好处是训练成本更低、显存占用更小，实现也相对简单；缺点是需要对同一个问题采样多条回答，训练效果依赖采样质量和奖励函数设计。

GRPO 可以看作 PPO 的一种变体。它保留了 PPO 中“用优势函数更新策略”和“通过 KL 约束防止模型跑偏”的思想，但把 PPO 里依赖 value model 估计 advantage 的方式，改成了同一个 prompt 下多条回答之间的组内相对比较，因此训练成本更低。


### SFT 数据如何筛选和采样

SFT 数据筛选我会重点看三类质量：指令质量、回答质量和格式质量。首先过滤低质量样本，比如无意义指令、重复样本、明显错误答案、格式不符合要求的数据；然后按任务类型做分桶，比如问答、推理、代码、工具调用、结构化输出、多轮对话等，避免某一类数据占比过高。

采样上不会简单随机采样，而是做混合采样和难例采样。通用能力数据保证模型基础能力，业务数据保证场景适配，高质量人工标注数据权重更高；同时会保留一部分失败样例或边界样例，让模型学习如何处理复杂输入。对于过长、重复、模板化严重的数据，会降权或截断处理。

如果是 Agent 场景，我会特别关注工具调用格式、结构化输出、拒答边界和多轮状态一致性，因为这些会直接影响后续 Workflow 是否能稳定消费模型输出。

### 为什么选 GRPO，优化目标是什么

GRPO 可以理解为一种不依赖价值模型的策略优化方法。相比PPO，它不需要单独训练 critic / value model，而是对同一个 prompt 采样多个回答，用组内奖励的相对优势来更新模型。这样可以降低训练成本和显存开销，比较适合大模型 RLHF 或推理能力优化场景。

它的优化目标本质上还是提高高奖励回答的生成概率，降低低奖励回答的生成概率，同时通过 KL 约束限制当前策略不要偏离参考模型太远，避免模型为了奖励过度漂移。


### 奖励函数如何设计

奖励函数设计我会分成结果奖励、过程奖励和约束奖励。

结果奖励看最终答案是否正确，比如数学题答案是否一致、代码是否通过测试、结构化输出是否能解析。

过程奖励看推理过程是否合理，比如步骤是否完整、是否有自洽逻辑、是否遵守工具调用流程。

约束奖励用于防止模型走偏，比如格式合法性、长度控制、安全合规、是否胡编、是否重复输出。

最后会把这些 reward 做加权组合，而不是只依赖单一指标。因为单一奖励很容易被模型钻空子。

### 如何判断强化学习训练质量达到要求

不能只看训练 reward，因为 reward 上升不代表真实能力提升，可能出现 reward hacking。

我会看四类指标：第一是验证集 reward，看是否在 held-out 数据上同步提升；第二是任务成功率，比如数学准确率、代码 pass rate、工具调用成功率；第三是人工或模型评审的质量指标，比如有用性、真实性、格式遵循率；第四是稳定性指标，比如 KL 是否过大、输出长度是否异常、重复率是否上升、拒答率是否异常。

如果 reward 上升，但验证集任务成功率不升，或者 KL、长度、重复率异常，就说明训练可能没有真正变好。

### reward hacking

Reward hacking 是强化学习里很常见的问题，指模型利用奖励函数的漏洞获得高分，但实际任务质量没有提升。比如奖励函数只看格式，模型就只保证格式正确；奖励函数偏好长回答，模型就输出冗长内容；奖励函数看关键词，模型就堆关键词。

解决方式通常是多维度奖励设计，不能只依赖单一指标；同时要加入负向约束，比如长度、重复率、事实性、安全性；还要用 held-out 验证集、人工抽检和对抗样本检查模型有没有学偏。训练过程中也要监控 reward 之外的指标，比如任务成功率、输出长度、重复率等等。


### KV Cache 原理

自回归推理时，每生成一个新 token，都需要用它去关注前面所有 token。如果每一步都重新计算历史 token 的 K 和 V，会重复计算。

KV Cache 的做法是在第一次计算时缓存历史 token 的 Key 和 Value。后续生成新 token 时，只计算新 token 的 Q/K/V，然后把新 K/V 追加到 cache，用新 Q 和历史 K/V 做 attention。这样可以把每步重复计算降下来，加速解码。

### 如果模型推理慢，如何排查

我会先区分是首 token 慢还是生成过程慢。首 token 慢通常和 prompt 长度、prefill、RAG、排队有关；每 token 慢通常和模型大小、decode、KV cache、显存和推理框架有关。然后看 GPU 利用率、显存、batch、上下文长度和输出长度，最后再看服务链路里是否有工具调用或检索阻塞。

## java八股

### 仔细介绍一下应用层的具体操作和实现细节

应用层主要负责任务生命周期管理，而不是具体生成。Controller 创建任务并返回 taskId；ApplicationService 异步执行各阶段，组装 ArticleState，注入 RAG 上下文，选择 Orchestrated Workflow；阶段完成后负责落库、更新 phase/status，并通过 EventPublisher 转换成 SSE 消息推给前端。标题和大纲确认由应用层状态机控制，从而接入 Human-in-the-loop。异常方面，ReviewRejectedException 和普通异常都会在应用层统一收口，更新任务失败状态、推送 ERROR 并关闭 SSE，避免异常泄漏到前端或任务悬挂。


## 通用

### 有什么场景适用于Agent

适合目标开放、步骤可变、需要工具调用、需要多轮反馈、需要规划和评审的任务，比如内容创作、研究分析、复杂客服、数据分析助手、自动化运营。

### 有什么场景不适合用Agent

不适合规则明确、低延迟、高确定性、强一致性和成本敏感的任务，比如简单CRUD、固定报表、支付结算、权限校验、核心交易链路。这类更适合传统代码和规则引擎。

### 对于模型选型，你是从什么角度去思考的

1. 按任务选模型：文本生成看语言能力、成本和流式支持；Review 看判断稳定性和结构化输出能力；图片评审要多模态能力；Embedding 看向量维度、召回效果和成本；文生图看质量、时延、可控性和接口稳定性。总体是能力、成本、时延、稳定性和可观测性之间做权衡。
