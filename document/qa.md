### 科研项目介绍

我这个课题做的是一个面向部分标注场景的鲁棒多标签图像识别方法，叫 UncertaintyCoOp。

这个任务的背景是：传统多标签分类方法默认所有标签都是完整且准确的，但在真实大规模数据集中，经常会出现标签漏标、错标的问题，同时模型对未见类别的泛化能力也比较弱，而且大多数方法默认监督信号是可靠的，没有显式建模不确定性，这会导致模型学到错误信息。

针对这个问题，我的核心思路是把“标签不可靠”显式建模出来。在方法上，我是在 CoOp 的 prompt learning 框架基础上做扩展，为每个类别设计了两类可学习提示：一个是表示正常语义的正向 prompt，一个是表示不确定性的 prompt，同时引入一个负向特征向量来提供对比信息。

模型会将图像特征分别和这三类提示做相似度计算，得到三种预测分布，然后通过一个基于信息熵和置信度的模块去估计当前预测的不确定性程度，再用这个不确定性系数去动态融合三种分布，得到最终结果。

另外，我还引入了一个“教师分布”机制，通过历史高置信预测进稳定约束，并结合 KL 散度做正则，同时在损失函数上使用 ASL 来降低容易样本的影响，从而整体提升鲁棒性。

最终这个方法的目标就是：在标签不完整甚至有噪声的情况下，让模型仍然能够稳定学习，并提升对未见类别的泛化能力。

### 项目中的Tool Calling实现

我们的项目采用了基于Spring AI的Tool Calling架构来实现智能配图功能。整个流程是：配图分析的智能体分析文章内容生成配图需求，然后通过@Tool注解定义的ImageGenerationTool工具进行配图服务调用，再按图片来源分组并行执行配图任务。这样子设计的优势在于可以把不同配图方式的逻辑进行解耦，易于后续扩展更多的配图方式，并且具备自动降级机制确保系统稳定性。

Tool Calling架构
1. 工具定义：通过 @Tool 注解定义工具，如 ImageGenerationTool
2. 工具调用：智能体通过Spring AI的Tool Calling功能自动调用配图工具
3. 参数传递：工具接收结构化的参数（图片来源、关键词、提示词等）
4. 结果返回：工具执行完成后返回结构化的JSON结果

配图Tool Calling流程
1. 配图分析：智能体4（ImageAnalyzerAgent）分析文章内容，生成配图需求
2. 工具调用：智能体5通过 ImageGenerationTool 调用不同配图服务
3. 并行执行：ParallelImageGenerator 按图片来源分组并行执行配图任务
4. 结果整合：将生成的图片URL插入文章对应位置

Tool Calling的优势
1. 解耦设计：配图逻辑封装在独立工具中，易于扩展
2. 智能决策：AI可以自主选择最合适的配图方式和位置
3. 并行处理：不同类型的配图可以并行生成，提升效率
4. 自动降级：配图失败时自动降级到备用方案

### 知道MCP吗？
MCP（Model Context Protocol）本质上是 Anthropic 提出的一个模型上下文协议，可以理解成“大模型调用外部工具的标准化协议”。
它解决的是 Tool Calling 里“工具接入不统一”的问题，把工具能力统一抽象成标准接口，让模型能够像调用 API 一样调用各种外部工具。
我理解它类似 AI 领域的 “USB 协议”——模型不用关心工具内部怎么实现，只需要按协议调用。
当时项目目标是验证 Multi-Agent 内容生成流程，所以我优先完成了核心能力闭环，包括任务编排、Tool Calling、RAG 和流式输出。
因为工具数量不多，而且都是我自己控制的内部工具，所以直接用 Spring AI 的 Tool Calling 成本更低，开发效率更高。
MCP 更适合“工具很多、来源复杂、需要标准化接入”的场景，比如多个团队共享工具生态的时候，它的价值会更明显。
如果升级到 MCP，我会把现有配图工具和知识检索能力封装成 MCP Server，对外暴露标准 Tool 接口。这样 Agent 通过 MCP Client 动态发现和调用工具，实现工具层解耦，提高扩展性和复用性。未来新增工具时不需要改 Agent 主流程，只需要注册新的 MCP Tool。

### RAG 的动机

在不同文本风格的创作过程中，除了通过 Prompt 做角色设定外，我还引入了一个轻量化的 RAG 模块。
不过这里的 RAG 不是传统知识问答式 RAG，而是 Generation-oriented RAG，主要用于给模型提供“写作素材”和“风格参考”。
做这个的动机主要有两个：
第一，单纯靠 Prompt 指定“请模仿小红书风格”这类方式，生成风格不够稳定；
所以我希望模型在生成前，先参考一些高质量风格样本，实现 style grounding。
第二，相比微调，RAG 的知识和风格样本可以动态更新，不需要重新训练模型，维护成本更低，也更适合内容创作场景。

### RAG的实现

在正文生成阶段，我设计了一个面向内容创作场景的轻量化 RAG 模块，它的目标不是做知识问答，而是给正文写作的Agent 提供“写作风格参考”。

首先在知识构建阶段，我会把高质量文章样本、写作模板和行业案例作为知识来源，统一整理成 Markdown 文档。然后进行 semantic chunking，优先按照标题、段落和文章结构进行切分，保证每个 chunk 本身是完整语义单元，避免固定长度切分导致语义断裂。

分块之后，使用 text-embedding-v3 对每个 chunk 做向量化，生成 embedding，并将文本内容、metadata 和向量一起存入 PGVector。其中 metadata 会记录文章来源、文章风格、主题标签等信息，方便后续过滤。

在检索阶段，用户输入创作需求后，我会先做一次Query Rewrite，把自然语言需求转换成更适合检索的结构化 query。

然后进入Hybrid Retrieval：一方面通过PGVector做dense retrieval，负责语义召回；另一方面通过PostgreSQL Full Text Search做BM25-like的关键词召回，负责命中热点词和关键术语。两路结果通过RRF（Reciprocal Rank Fusion）在应用层进行融合，避免不同检索器score不可比的问题。

没有做Rerank是因为这里做RAG的目的更多的是提供一个写作风格的参考，并且需要尽可能减少耗时，从trade-off的角度考虑，最终只采用了top-k，没有进行重排。

最后，把这些检索结果动态注入到正文写作Agent的context中，让模型在生成正文时既参考风格样本，也参考相关内容，从而提升文章的一致性、可控性和生成质量。

### 为什么选择PGVector

因为我的核心诉求是快速开发、还有满足基础语义检索能力。同时很多传统业务都会把数据存储在关系型数据库中，直接给原有的数据库安装扩展就能实现向量相似度搜索、而不需要额外搞一套向量数据库。

### RAG优化方案

由于知识库规模不大，暂时没有加 rerank，但如果规模扩大，我会考虑cross-encoder rerank；混合检索也是下一步优化方向，比如向量 + BM25。


### 介绍一下项目的后端整体架构?

这个项目的核心业务是让用户输入一个选题，AI通过多个智能体协作，自动生成一篇带配图的文章。用户还能在创作过程中参与标题选择和大纲编辑，实现人机协作。

整个后端采用了分层架构的设计，从上到下分为五层。最上面是接入层，用Vue3+Nginx做前端渲染和请求转发。接口层用Spring Boot对外提供RESTful API，同时引入了SSE做流式推送、AOP做权限控制和日志。

业务层是最核心的部分，包含几个关键模块:用户模块负责注册登录和权限管理;文章模块负责任务创建、状态流转和内容存储;智能体模块是技术核心，基于SpringAIAlibaba封装了5个AI智能体的调用逻辑;配图模块基于策略模式管理6种不同的配图方式;此外还有Stripe支付模块和统计分析模块。

再下面是智能体层，5个智能体分别负责标题生成、大纲生成、正文创作、配图分析和配图生成，它们之间通过共享的ArticleState状态对象传递数据。最底层是数据层，MySQL存业务数据，Redis存Session和缓存，腾讯云COS存配图文件。

这些模块的交互流程大致是:用户登录后创建一个创作任务，系统生成taskId 立即返回，然后后台异步启动智能体流水线。5个智能体按顺序执行，配图阶段还会并行调用多个配图服务。整个过程通过SSE实时推送进度，用户能看到文章一步步生成出来。

### MyBatis-Flex 和 MyBatis Plus 有什么区别? 为什么选它?

这两个框架本质上都是对MyBatis的增强，帮助开发者简化CRUD操作。但MyBatis-Flex有几个比较明显的优势

首先是更轻量，它除了MyBatis本身没有引入任何第三方依赖，可控性和稳定性更好。其次是性能，它在SQL执行过程中没有拦截器和SQL解析的开销，官方宣称性能有数量级的提升。还有就是Querywrapper更灵活，原生支持多表关联查询，不像MyBatis Plus 得依赖额外插件。

我们在项目中选择MyBatis-Flex，一方面是想丰富技术栈、学习有竞争力的新框架，另一方面也看重它的性能优势。它内置的雪花算法ID生成策略也很方便，通过 @Id(keyType = KeyType.Generator, value = KeyGenerators.snowFlakeId) -个就定了。

### 项目中Redis用在了哪些场景?

主要用在三个地方。

第一个是分布式Session管理。集成了 
spring-session-data-redis之后，用户的登录状态存到了Redis里。这样服务重启不会丢失Session，后续如果要做多实例水平扩展也没问题。

第二个是统计数据缓存。管理员查看的创作统计数据(今日创作量、成功率、活跃用户数之类的)计算起来涉及多张表的聚合查询，比较耗数据库。所以我在StatisticsServiceImpl里用Redis做了1小时的缓存，第一次算完存进去，后面直接读缓存就行了。

第三个是VIP配额管理。普通用户有5次创作的配额限制，VIP无限。配额的查询和扣减都通过Redis来操作，避免频繁访问数据库。

### Spring AI Alibaba在项目中起什么作用?怎么跟大模型集成的?

SpringAIAlibaba是这个项目的AI基础框架，它封装了跟通义千问大模型交互的所有细节，让我不用去处理底层的HTTP请求和JSON解析。

集成方式其实挺直接的。首先在配置文件里配好DashScope的APIKey，框架会自动创建 DashscopechatModel的Bean。然后在代码里就可以直接注入使用了。

调用方式分两种。对于标题生成、配图分析这种需要拿到完整结果再处理的场景，我用的是同步调用 chatModel.cal1(prompt)，等AI返回完整JSON后再解析。对于大纲和正文这种需要实时展示给用户看的场景，用的是流式调用chatModel.stream(prompt)，它返回一个Flux<ChatResponse>，我订阅这个流，每收到一个Token就通过SSE推给前端，这样用户就能看到打字机效果。

Prompt 的管理也做了统一，所有智能体的系统提示词都集中在PromptConstant类里，用{mainTitle}、{content}这样的占位符做参数化，运行时替换成实际内容。对于需要返回结构化数据的智能体，我在Prompt里明确要求了JSON格式，然后用Gson解析成对应的Java对象。

### 描述一下项目中多智能体协作创作文章的完整流程?

整个创作过程由5个智能体像流水线一样串行协作完成，它们通过一个共享的 ArticleState状态对象来传递中间数据。

首先是智能体1负责生成标题。它拿到用户的选题后，调用大模型生成3到5个标题方案，包含主标题和副标题。然后系统会暂停下来等用户选择，用户挑一个满意的标题，还可以顺便输入补充描述来指导后续创作方向。

用户确认标题后，智能体2开始生成大纲。它根据选定的标题和补充描述，用流式调用生成JSON格式的大纲结构。用户拿到大纲后可以拖拽排序、增删章节，甚至让AI根据修改建议重新优化。

大纲确认后进入智能体3正文创作环节。它根据标题和大纲逐段生成Markdown格式的正文，整个过程通过SSE实时推送，用户能看到文章逐字出现。

正文写完后，智能体4会分析全文，确定哪些位置需要配图、用什么类型的图。它会在正文中插入占位符来标记图片位置，普通图片用{{IMAGE_PLACEHOLDER_N}}，行内图标用{{IcON PLACEHOLDER_N}}。这里有个设计要点:封面图(position=1)不需要占位符，它通过独立的coverImage字段单独存储，这样前端可以灵活地在列表卡片、文章顶部等不同位置展示封面图。

最后智能体5根据配图需求列表，按图片来源并行调用各个配图服务，拿到图片后统一上传到腾讯云COS。全部配图就位后，执行图文合成，把占位符替换成真实的图片链接，生成最终的完整图文。

### 项目后端的SSE流式推送具体是怎么实现的?

我用的是Spring MVC内置的SseEmitter，整体思路是"创建连接推送消息关闭连接"。

首先在 SseEmitterManager 里用一个 ConcurrentHashMap<String,SseEmitter> 来管理所有活跃的SSE连接，key是taskId。当前端调用进度接口时，后端创建一个SseEmitter实例并注册进去，超时时间设为30分钟。

智能体执行过程中，每当有新内容产生，就调用 sseEmitterManager.send(taskId，message)往对应的连接推数据。为了让前端能区分不同类型的消息，我设计了一个sseMessageTypeEnum 枚举，包含了 AGENT2_STREAMING(大纲流式输出)、AGENT3_STR(正文流式输出)、(单张配图完成)、TITLES_GENERATEDEAMINGIMAGE COMPLETE(标题方案就绪)、OUTLINE_GENERATED(大纲就绪)、ALL_COMPLETE(全部完成)、ERROR(出错)等消息类型。

每条SSE消息的格式大致是类型前缀:实际内容，前端收到后先提取消息类型，再根据类型决定怎么处理--流式内容就追加显示，结构化数据就解析JSON更新状态。

还有个细节:SSE连接出错或超时时，SseEmitter会触发回调，我在回调里做了连接的清理工作，避免Map里积累太多无效连接。

### 项目中异步任务处理是怎么设计的?为什么用自定义线程池?

AI创作一篇文章可能要几十秒甚至更长，如果让用户在接口上一直等肯定不行。所以我设计了一个"快速返回+异步执行+SSE推送"的模式。

用户发起创作请求后，Controller只做参数校验、创建数据库记录、生成taskId:然后马上返回。真正耗时的创作逻辑放在 ArticleAsyncService 里，用@Async("articleExecutor")标注，Spring会把它丢到专门的线程池里去跑。前端拿到taskId后建立SSE连接，后台创作到哪一步就推到哪一步。

为什么要自定义线程池而不用Spring默认的?因为默认的SimpleAsyncTaskExecutor每次都创建新线程，没有线程复用，也没有任务队列的限制，在高并发场景下可能把系统资源耗尽。

我在AsyncConfig里配了一个ThreadPoolTaskExecutor:核心线程5个，最大线程10个，队列容量100。核心线程5个意味着同时能处理5个创作任务，由于AI调用是I/O密集型(大部分时间在等大模型响应)，线程并不会占用太多CPU。队列容量100保证了突发流量时任务不会被直接拒绝。拒绝策略选的是callerRunsPolicy，队列也满了的话就让调用方自己执行，这是一种比较稳妥的兜底方案。

### 项目中ArticleState这个状态对象是怎么在各智能体之间流转的?

ArticleState相当于是整条创作流水线的"传送带"，每个智能体从上面取走自己需要的东西，加工完了再放回去。

它是一个普通的可序列化Java对象，里面的字段覆盖了创作全流程的数据:从最初的taskId 和 topic，到智能体1产出的titleoptions，用户选的title 和userDescription，智能体2的outline，智能体3的content，智能体4的 imageRequirements，一直到智能体5的images 和最终合成的fullcontent、coverImage 。

流转方式很直接-创作开始时，ArticleAsyncService 创建一个ArticleState实例，设好初始值，然后把它依次传给每个智能体方法。智能体1读topic、写titleoptions;用户选择后设置title;智能体2读title、写 outline;依此类推。每个智能体只关心自己那几个字段，不需要知道其他智能体的存在。

这种设计的好处是解耦-如果要加一个新智能体，只需要在 ArticleState里加几个字段，不用改已有智能体的代码。而且因为是一个对象引用在方法间传递，没有额外的序列化开销。

### 什么是策略模式?项目中怎么用策略模式实现多种配图方式的扩展?

策略模式简单来说就是把一组可替换的算法封装成独立的类，让它们可以互相替换，调用方不需要关心具体用的是哪个算法。

在我们项目里，配图是一个典型的策略模式应用场景。系统支持6种配图方式-Pexels图片搜索、Nano Banana AI生图、Mermaid流程图、Iconify图标、表情包搜索、SVG概念示意图，每种方式获取图片的逻辑完全不同，但对外提供的能力是一样的:给定需求，返回图片。

具体实现分三层。首先是统一接口 Imagesearchservice，它定义了所有配图服务必须实现的方法:getImage()获取图片URL、getImageData()获取图片数据、getMethod()返回自己对应的配图方式枚举、isAvailable()检查服务是否可用。

然后是6个具体实现类，每个类封装了自己独特的获取图片逻辑。比如 PexelsService 调用Pexels API搜索图片，NanoBananaService 通过Google Gen AI SDK 生成图片， Mermaidservice 调用 mermaid-cli 把 Mermaid 代码渲染成图片,SvgDiagramservice则让大模型生成SVG代码再转换为图片。

最关键的是策略选择器ImageServiceStrategy。它在启动时通过@PostConstruct自动发现Spring容器中所有 ImageSearchService 的实现，以 ImageMethodEnum 为key注册到一个EnumMap里。对外提供getImageAndupload()方法，调用方只需要传入配图方式和请求参数，选择器自动找到对应的服务实现、获取图片、上传到COS、返回结果。

这样做最大的好处是扩展性极强-未来要加一种新的配图方式，只需要写一个新的ImageSearchService 实现类加上 @Component 注解，选择器就能自动发现并注册它，完全不用改已有代码。

### 项目中ImageData统一数据封装是怎么设计的?解决了什么问题?

不同配图服务返回的图片数据格式五花八门-Pexels返回的是图片URL，Nano Banana返回的是原始字节流，Mermaid渲染出来的是本地文件的字节数据，SVG图是base64编码的dataURL。如果不做统一封装，上层代码就得到处写if-else判断是哪种格式，再分别处理，代码会非常混乱。

为了解决这个问题，我设计了一个ImageData类来统一封装所有图片数据。它内部定义了一个DataType 枚举来标识数据类型(BYTEs、URL、DATA_URL)，并提供了三个静态工厂方法fromBytes()、fromDataurl()方便创建实例。fromUrl()
关键在于它提供了一个统一的 getImageBytes()方法。不管底层数据是什么格式，调用这个方法都能拿到图片的字节流--URL类型会自动下载，dataURL会自动解码base64，字节类型直接返回。这样上传到COS的逻辑就完全统一了，cosService.uploadImageData() 只需要调用 getImageBytes()就行，不用关心图片从哪来。

此外 ImageData 还提供了 isValid()校验方法和 getFileExtension()方法，方便上层判断数据有效性和确定文件扩展名。整个设计遵循了封装变化的原则，把格式差异完全隐藏在了类的内部。

### 项目配图服务的自动降级是怎么实现的?

在实际运行中，外部配图服务不一定总是可用的--APIKey没配、服务商限流、网络超时都可能导致某个配图服务暂时不能用。如果某张图获取失败就让整篇文章创作失败，用户体验会很差。所以我设计了一套自动降级机制。

这个机制分两层。第一层是服务可用性检查。每个ImageSearchService实现类都可以重写isAvailable()方法，在里面检查必要的配置是否齐全。比如 PexelsService会检查APIKey是否配置了，Mermaidservice 会检查 mermaid-cli 命令是否可用。ImageServiceStrategy 在选择服务时会先检查可用性，如果目标服务不可用，直接降级到兜底方案。

第二层是运行时异常降级。即使服务可用性检查通过了，实际调用过程中仍然可能出错(比如搜索关键词没找到结果、AI生图超时等)。这时候ImageServiceStrategy的 getImageAndupload() 方法会catch住常，自动调用 getFallbackImage() 方法获取兜底图片。

兜底方案用的是 Picsum (https://picsum.photos/800/600?random={position} ),它免费、稳定、不需要APIKey，能根据参数返回随机的高清图片。虽然跟文章内容不一定相关，但至少保证了文章的排版是完整的，不会出现破图。

这两层降级机制组合起来，保证了整个配图流程的高可用性--不管外部服务出什么问题，文章创作都能完整走完。

### 项目占位符方案是怎么实现图文精确合成的?

早期版本的图文合成比较粗糙，就是遇到章节标题就在后面插一张图。但这种方式太死板了，不能在段落中间、列表里面插图，更不能在文字行内放小图标。所以后来我重构了配图方案，改成了占位符方案。

核心思路是让智能体4在分析配图需求时，同时在正文中插入占位符来精确标记每张图片的位置。系统支持两种占位符格式:{{IMAGE_PLACEHOLDER_N}}必须独占一行，用于普通图片;{{IcON_PLAcEHOLDER_N}}]可以出现在文字行内，专门用于Iconify图标这种小型装饰图。

智能体4返回的数据结构是 Agent4Result，包含两个核心字段:contentWithPlaceholders 是插入了占位符的正文，imageRequirements 是配图需求列表。每个需求项里有一个placeholderId字段，记录它对应的占位符标识。有个特殊情况是封面图(position=1)，它的 placeholderId 为空，因为封面图不出现在正文中，而是通过coverImage字段独立存储。

图文合成的逻辑在mergeImagesIntoContent()方法里，核心就是遍历正文的每一行，检查有没有占位符，有的话就替换成对应的Markdown图片链接![描述](ur1)。对于行内的{{ICON_PLACEHOLDER_N}}，替换后它就会内嵌在文字中间，呈现为行内图标的效果。

这种方案的优势在于灵活性-图片位置完全由AI根据内容语义来决定，可以出现在任意合适的地方，比固定规则自然得多。

### 什么是Humaninthe Loop?项目中是怎么实现三阶段人机协作的?

Human in the Loop(人在回路中)是AI应用设计中的一个重要理念，核心思想是在AI自动化流程中引入人工干预节点，让人类在关键决策点上进行审核和修正。这样既利用了AI的高效生成能力，又通过人工把关保证了输出质量。

在我们项目中，整个创作流程被拆成了三个阶段，每个阶段之间都有一个人工确认的环节:

第一阶段是标题选择。智能体1生成3-5个标题方案后，系统暂停下来等用户选择。用户可以挑选最满意的标题组合，还能输入一段补充描述，比如"希望文章偏技术深度"或者"面向初学者"，这些信息会传给下一个智能体，影响大纲的生成方向。

第二阶段是大纲编辑。智能体2根据标题和补充描述生成大纲后，再次暂停等用户确认。用户可以对大纲做各种编辑-拖拽排序调整章节顺序、添加或删除章节、甚至点击"AI修改"按钮，输入修改建议让AI重新优化大纲结构。

第三阶段是正文和配图的自动生成。用户确认大纲后，后面的智能体5、4、3就全自动执行了，用户只需要通过SSE实时观看生成过程。

在后端实现上，我用ArticlePhaseEnum 枚举来管理任务阶段的流转:PENDING>TITLE GENERATING > TITLE SELECTING > OUTLINE GENERATING > OUTLINE EDITING > CONTENT GENERATING。每个确认操作(confirmTitle、confirmoutline)都会先校验当前阶段是否正确，防止越阶段操作，然后更新阶段状态并异步启动下一阶段。这种状态机的设计保证了流程的有序性和幂等性。

### 项目中任务状态机是怎么设计的?如何保证各阶段操作的有序性?

整个创作流程本质上是一个有限状态机，我用 ArticlePhaseEnum枚举来定义6个阶段:PENDING(待处理)、TITLE GENERATING(标题生成中)、TITLESELECTING等待用户选择标题）、OUTLINE GENERATING(大纲生成中)、OUTLINE EDITING(等待用户编辑大纲)、CONTENT GENERATING(正文生成中)。

状态流转是严格单向的。每次阶段变化都通过 ArticleService.updatePhase()来更新数据库中的 phase字段。而且每个操作在执行前都会校验当前阶段是否匹配，比如confirmTitle()会先检查当前是否处于TITLESELECTING 阶段，如果不是就直接拒绝。这样即使前端出bug发了重复请求，后端也不会出问题。

人工交互的衔接也是通过状态来驱动的。智能体1生成完标题后，系统会把状态改为TITLE_SELECTING 并通过SSE推送TITLES_GENERATED 消息。前端收到后展示选择界面。用户点确认后，后端校验状态、更新为oUTLINE_GENERATING、异步启动智能体2。大纲阶段同理。

这种设计的好处是状态清晰、可追溯。任何时候查数据库就能知道一个任务走到了哪一步。而且每个操作都有前置状态校验，天然保证了幂等性。

### 项目中AI修改大纲功能是怎么实现的?

在大纲编辑阶段，用户除了可以手动拖拽排序和增删章节外，还能让AI帮忙修改。用户输入一段修改建议(比如"合并前两个章节"或"加一个总结章节")，系统会把当前大纲和修改建议一起发给大模型，让它返回优化后的新大纲。

后端实现在 ArticleAgentService.aiModifyoutline()方法里。它会先校验当前任务是否处于ouTLINE_EDITING阶段，然后构造一个特殊的Prompt，把现有的大纲JSON和用户的修改建议拼在一起，要求AI返回修改后的完整大纲JSON。

拿到AI返回的新大纲后，解析成 outlineResult 对象并更新到ArticleState和数据库中，同时通过SSE把新大纲推给前端。前端收到后刷新大纲编辑界面，用户可以继续调整或确认。

这个功能属于VIP特权，普通用户只能手动编辑大纲。权限判断在ArticleService层做的，调用前会检查用户的角色。

### 项目中Stripe支付集成的完整流程是怎样的?Webhook的幂等性怎么保证?

项目的VIP购买功能集成了Stripe支付。整个流程可以分为三步:创建支付会话一用户完成支付Webhook回调确认。

第一步，用户点击购买VIP后，前端调用 PaymentController 的 createvipPaymentsession 接口。后端调用Stripe SDK创建一个Checkout Session，在里面设置好商品信息(VIP永久会员，$199)、成功和取消的跳转URL。关键的一步是在Session的metadata里塞入 userId和 productType，这样Webhook回调时能知道是哪个用户买的什么。创建完成后把SessionURL返回给前端，前端跳转到Stripe的支付页面。

第二步，用户在Stripe页面完成支付后，会被跳转回成功页面。但这只是前端的跳转，不能作为支付成功的依据，因为用户可能关掉浏览器或者网络中断.

第三步才是真正确认支付的环节。Stripe会向我们配置的Webhook地址 posT/webhook/stripe 发送事件通知。 StripeWebhookController 收到后，首先用webhook.con做签名验证，确保请求确实来自Stripe而不是伪造的。然后根据事件structEventO类型 ( checkout.session.completed ) 提取 Session 信息, 调用 PaymentService.handlePaymentsuccess()处理业务逻辑。

幂等性保证是这样做的:handlePaymentsuccess()会先根据stripeSessionId查找支付记录。如果记录的状态已经是succEEDED，说明之前已经处理过了，直接返回不做任何操作。只有状态为 pENDING时才执行后续的升级逻辑-更新支付记录状态、给用户设置VIP角色和VIP时间。整个过程用@Transactional保证原子性，避免出现"钱收了但VIP没开通"的情况。

### 项目中VIP会员的权限控制是怎么实现的?配额和功能上有什么差异?

VIP权限控制分两个维度:创作配额和功能权限。

配额方面，普通用户每天有5次创作额度，VIP用户无限。配额的查询和扣减逻辑在QuotaServiceImpl里，核心思路很简单- hasQuota()方法先判断用户角色，如果是VIP直接返回true;普通用户再去查Redis里剩余配额。consumeQuota()也是一样，VIP用户直接跳过，普通用户才真正扣减。

功能权限方面，主要体现在配图方式的差异化。6种配图方式中，Pexels图片搜索和Iconify图标对所有用户开放，而Nano Banana AI生图、Mermaid流程图、表情包搜索、SVG概念示意图这些高级配图方式只有VIP用户能用。另外AI修改大纲功能也是VIP专属。

实现上，用户创建任务时选择的配图方式会经过 processImageMethods()方法处理。这个方法会检查用户角色，如果不是VIP就过滤掉高级配图方式，只保留基础的。这样即使前端没做好限制，后端也能兜住。前端在UI层面也做了处理，非VIP用户看到高级配图方式时会显示锁定图标和"VIP专属"标签。

### 项目中如何使用AOP实现智能体执行日志的自动记录?

每次创作任务会依次调用5个智能体，每个智能体的执行耗时、成功失败、输入输出这些信息对于监控和优化都很重要。但如果在每个智能体方法里都手动写日志代码，一方面很繁琐，另一方面也违反了单一职责原则。所以我用AOP来做自动化记录。

首先定义了一个@AgentExecution注解，有两个属性:value是智能体名称，description 是描述信息。把这个注解标记在每个智能体方法上就行了。

然后写了一个AgentExecutionAspect 切面类，用@Around 环绕通知拦截所有标了@AgentExecution的方法。在方法执行前记录开始时间，执行完记录结束时间和状态，出异常也能捕获到错误信息。最后构造一个 AgentLog 对象，包含taskId、errorMessage等字段，通过 @Async 异步保存agentNamedurationMs 、status、到数据库。

异步保存是个重要的设计决策。日志写入是非核心逻辑，如果同步写入的话，一旦数据库慢了就会拖累创作主流程。用 @Async 把日志保存丢到另一个线程池里，即使保存失败也不影响文章生成。

taskId的提取也有讲究。切面通过反射遍历方法参数，找到ArticleState类型的参数，从里面取出 taskId。这种方式不需要方法签名做任何调整，对业务代码是完全无侵入的。

有个技术细节值得一提:由于SpringAOP基于代理机制，同一个类里方法互相调用是不会经过代理的，也就拿不到AOP增强。为了解决这个问题，我开启了 @EnableAspectJAutoProxy(exposeProxy= true)，在需要的地方通过 AopContext.currentProxy()获取当前代理对象来调用方法，确保AOP切面能正常生效。

### 项目中统计分析功能的缓存策略是怎么设计的?

管理员的统计面板需要展示今日/本周/本月创作量、成功率、平均耗时、活跃用户数、VIP用户数等一系列指标。这些指标的计算涉及article、user、agent_loguser多张表的聚合查询，如果每次打开面板都去数据库实时算，既慢又浪费资源。

所以我在 StatisticsServiceImpl 里做了Redis缓存。缓存key是statistics:overview，过期时间1小时。请求进来先查Redis，命中就直接返回;没命中就去数据库算一遍，算完存进Redis。

为什么设1小时而不是更短或更长?这是个权衡。统计数据不需要实时精确，1小时的延迟在运营场景下完全可以接受。如果设太短，比如1分钟，缓存的意义就不大了，大部分请求还是打到数据库。如果设太长，比如1天，管理员看到的数据会太过陈旧。

缓存的值是整个Statisticsvo对象序列化后存的，这样一次Redis读取就能拿到所有指标，不用分开缓存。更新策略采用的是惰性更新-过期后下一次请求触发重新计算，没有额外的定时任务。如果后续访问量大到需要更精细的控制，可以考虑加一个定时刷新机制来避免缓存穿透后的瞬间高并发。

### 项目为什么要引入Spring AI Alibaba 的StateGraph来编排多智能体?之前的方式有什么问题?

项目早期的智能体编排方式比较朴素-就是在ArticleAgentService 里按顺序一个个调方法，类似于一个大的编排函数。这种方式能跑通，但随着项目复杂度上升，几个痛点就暴露出来了。

第一个问题是流程跟业务逻辑耦合。智能体的调用顺序、错误处理、状态更新全部写在一个方法里，代码越来越长，改一个地方很容易影响到其他地方。第二个问题是扩展性差。比如想在大纲生成之后加一个"大纲质量检查"节点，或者想让配图分析和正文创作并行执行，在原来的代码结构里很难优雅地实现。第三个问题是配图生成是串行的，一张一张生成很慢，但改成并行又需要手动管理线程和结果收集，代码复杂度上去了。

引入 StateGraph 之后，这些问题就迎刃而解了。StateGraph 是 Spring AI Alibaba 提供的多智能体编排框架，思路是把每个智能体定义为图中的一个节点(实现 NodeAction接口)，然后通过边来定义节点之间的执行顺序。编排逻辑变成了一张清晰的图，而不是一坨if-else。

每个节点只需要关注自己的事情--从状态对象里取输入、干活、把输出写回状态对象。节点之间通过 overAl1State 状态对象来传递数据，跟之前的 ArticleState思路类似，但变成了key-value的Map结构。

最关键的是，StateGraph让并行执行和条件分支变得很容易。我把配图生成节点改成了并行执行(按图片来源分组，组间并行、组内串行)，创作速度有了明显提升。而且如果未来要加质量检查、重试等逻辑，只需要在图上加节点和边就行了。

### 描述一下项目中StateGraph编排后的核心节点和数据流转?

我把整个创作流程拆成了三个独立的Graph，对应Humaninthe Loop的三个阶段。

第一个Graph(阶段1)只有一个节点:TitleGeneratorAgent。它从状态中读取topic和 style，调用大模型生成标题方案，把titleoptions写回状态。执行完后系统等待用户选择。

第二个Graph (阶段2)也只有一个节点:outlineGeneratorAgent。它读取 mainTitle、subTitle、 userDescription 和 style，通过流式调用生成大纲，把 outline写回状态。这里有个特殊之处，大纲需要流式输出给前端，但StateGraph里不能直接传Consumer<String>这种函数式对象(因为涉及序列化问题)，所以我用了StreamHandlerContext(基于ThreadLocal)来传递流处理器。

第三个Graph(阶段3)是最复杂的，包含多个串行节点:ContentGeneratorAgent- ImageAnalyzerAgent - ParallelImageGenerator - ContentMergerAgent 。正文创作完后，配图分析智能体确定需要哪些图和在哪插入，然后配图生成节点并行获取所有图片，最后合并节点把占位符替换为真实图片链接。

数据在节点之间通过 overAllState流转。每个节点从状态Map里取自己需要的key，处理完把结果写回新的key。状态更新策略统一使用 ReplaceStrategy，即新值直接覆盖旧值。

ArticleAgentorchestrator负责管理这三个Graph的构建和执行。为了平滑过渡，还做了一个配置开关article.agent.orchestrator.enabled，可以在新旧编排模式之间切换。

### 项目并行配图生成是怎么实现的?性能提升了多少?

在原来的串行方案里，如果一篇文章需要5张图，每张图获取+上传耗时3-5秒，总共就要15-25秒，这在整个创作流程里是相当大的一块耗时。

改成并行之后，我在 ParallelImageGenerator 里按图片来源(imageSource)对配图需求进行分组。组间是并行的-比如同时调Pexels搜图、Nano Banana生图、Mermaid渲染图。组内是串行的-如果有两张图都要从Pexels搜，它们还是一张张来，这是为了避免对同一个外部API造成过大的并发压力。

技术上用的是Java的completableFuture。对每组任务创建一个completableFuture.supplyAsync()，然后用 CompletableFuture.all0f()等待所有组执行完成。结果收集用的是copyonwriteArraylist，因为多个线程会同时往里面写结果，需要线程安全。

每张图片获取完成后还会通过SSE单独通知前端，这样用户能看到图片一张张加载出来，而不是等全部完成才显示。

性能提升取决于配图需求的分布情况。如果5张图来自5个不同的来源，理论上从25秒降到5秒左右，提升了5倍。实际场景中通常有3-4个不同来源，耗时大约能缩短 60%-70%。

### 项目中StreamHandlerContext 用ThreadLocal传递流处理器解决了什么问题?

这是一个比较巧妙的设计，解决的是StateGraph节点中无法直接传递函数式对象的问题。

背景是这样的:大纲和正文生成这两个智能体需要流式输出，也就是边生成边推送给前端。在原来的非Graph方案里，直接把一个Consumer<String>类型的回调函数作为参数传给智能体方法就行了。但在StateGraph中，节点之间的数据是通过 overAl1State 传递的，而overAl1State 本质是一个Map，值需要能序列化。Consumer<String>是一个函数式接口，放不进Map里。

StreamHandlerContext 就是用来绕过这个限制的。它是一个基于ThreadLocal的静态工具类，提供set()、get()、clear()三个方法。在Graph执行前，把流处理器通过 StreamHandlerContext.set(handler) 存到当前线程的 ThreadLocal里。节点内部执行时，通过StreamHandlerContext.get()取出处理器，然后正常调用就行了。Graph执行完后再clear()清理，防止内存泄漏。

这种方式的好处是对StateGraph的框架机制完全透明，不需要改框架代码，也不影响节点的可测试性(测试时mock一个handler set进去就行)。

### 项目中article表的设计思路是什么?索引是怎么考虑的?

article表是项目的核心业务表，存储了文章创作任务的全量数据。字段设计主要围绕创作流程的各个产物来的:taskId是唯一任务标识，userId 关联创建者，topic 存用户选题，mainTitle 和 subTitle 存选定的标题，outline 用JSON格式存大纲结构，content 存Markdown正文，fullcontent存最终的完整图文(含配图链接)，coverImage 单独存封面图URL，images 用JSON数组存所有配图信息，status和phase分别管理任务状态和阶段。

索引方面主要考虑了几个核心查询场景:

idxuserId是最基础的，用户查自己的文章列表、按用户统计创作量都会用到。idxstatus 用于按状态筛选，比如查所有失败的任务。idx createTime 用于按时间排序和范围查询，管理员看全量数据时常用。idxuserId_status是个联合索引，覆盖了"查某个用户在某个状态下的文章"这种组合查询。taskId上加了唯一索引，既保证了任务ID的唯一性，也让根据 taskId的单条查询非常快。

这里有个设计决策值得说一下:outline和images字段用的是JSON类型而不是拆成关联表。因为大纲和配图信息总是跟文章一起读写的，很少需要单独查某一个章节或某一张图片，用JSON存储省去了多表关联的开销，代码也更简洁。

### 项目中agent_log表的设计思路是什么?agent_1og表用来存储每次智能体执行的详细日志，主要服务于监控分析和问题排查。

每条记录对应一个智能体在一次创作任务中的一次执行，关键字段有:taskId关联agentName 记录是哪个智能体，到对应的文章任务，，记录执startTime  endTime行时间窗口，durationMs记录毫秒级耗时，status记录成功或失败，errorMessage在失败时记录错误信息，inputData和 outputData用JSON格式存储智能体的输入输出数据(方便排查问题时回放上下文)。

索引设计上，idx_taskId用于查某次创作任务的全部智能体日志，这是最常用的查询场景-一篇文章出了问题，先查它的所有智能体日志看哪步出错了。idx_agentName用于分析某个智能体的整体表现，比如统计"配图分析智能体的平均耗时"。idxstatus用于快速筛选失败的记录。idxcreateTime用于时间范围查询。

一次完整的创作任务通常会产生5条 agent_1og记录，数据量增长比较快。如果后续数据量大了，可以考虑按时间做分区或者定期归档历史数据。

### 项目中如何使用AOP+自定义注解实现权限控制?

项目中有些接口只有管理员能访问(比如统计面板)，有些只有VIP用户能用(比如退款接口)。如果每个Controller方法里都写一遍权限校验代码，太繁琐也容易遗漏。所以我用了AOP+自定义注解的方式来统一处理。

首先定义了一个@Authcheck注解，它有一个mustRole属性，用来指定该接口要求的最低角色。用的时候直接标在Controller 方法上，比如@AuthCheck(mustRole="admin")或者@AuthCheck(mustRole ="vip")。

然后写了一个AuthInterceptor 切面类，用@Around("@annotation(authCheck)")拦截所有标了 @Authcheck 的方法。切面逻辑很清晰:先从HttpServletRequest 中获取当前登录用户信息，再把用户的角色跟注解里要求的角色做比较，权限不足就抛自定义异常，通过了才放行执行原方法。

获取HttpServletRequest有个小技巧-通过遍历方法参数列表找到HttpServletRequest类型的参数。这样做比从Spring上下文里取更直接。

这种方式的好处是声明式的，看一眼方法签名上的注解就知道它需要什么权限，比在方法体里藏一段权限校验代码直观得多。而且如果后续权限体系变复杂了(比如引入更细粒度的权限)，只需要改切面逻辑和注解定义，业务代码不用动。

### 项目如何优化调用AI接口的SSE流式输出效果?

在实现SSE流式输出时，有几个实际遇到的问题和优化措施。

第一个问题是数据丢失。标准的SSE协议里，连续的空格或特殊的换行符在传输过程中可能会丢失或被浏览器错误解析。为了解决这个，我把每个数据块封装在一个JSON对象里传输，前端收到后再从JSON中提取原始数据。这样不管内容里有什么特殊字符都能完整传过去。

第二个问题是流结束的判断。SSE连接断开时会触发 onerror或 onclose事件，但这些事件没法区分是正常结束还是网络异常中断。所以我在所有数据发送完毕后，额外发送一个ALL_COMPLETE类型的消息，作为正常结束的明确信号。前端收到这个消息后才关闭连接、触发后续的保存和展示逻辑。

第三个问题是消息类型的区分。由于创作过程涉及多个阶段，前端需要知道当前推送的是标题方案、大纲流式内容、正文流式内容还是配图进度。我通过SseMessageTypeEnum给每条消息加了类型前缀，前端解析出类型后分别处理。这样一个SSE连接就能承载整个创作流程的所有进度信息，不需要建立多个连接。


### 描述一下Al爆款文章创作器项目前端的核心业务流程?

前端的核心业务就是围绕”创建文章人机交互实时展示查看管理”这条主线来的。

用户进入创作页面后，输入选题、选择文章风格和配图方式，点击创建。前端调用后端接口拿到taskId，然后立刻用EventSource建立SSE长连接，开始监听后端推送的进度消息。

接下来前端会经历三个交互阶段。第一阶段收到TITLES_GENERATED消息后，展示标题选择界面，用户挑选标题并可以输入补充描述，然后调用确认接口。第二阶段收到OUTLINE_GENERATED消息后，展示可编辑的大纲界面，用户可以拖拽排序、增删章节、请求AI修改，满意后确认。第三阶段就是自动生成了，前端实时接收正文的流式内容和配图进度，用打字机效果展示出来。

创作完成后，用户可以在文章列表页查看所有已创作的文章，支持搜索和状态筛选。点进某篇文章能看到完整的图文内容，还可以导出为Markdown文件。

整个前端的状态管理用的 Pinia，路由用Vue Router，UI组件库是Ant Design Vue。页面的状态切换(输入、创作中、各阶段交互、完成)通过响应式变量和计算属性来驱动。

### 项目前端怎么处理SSE流式通信?打字机效果是怎么实现的?

前端用的是浏览器原生的EventSource API来接收SSE消息。创建连接时传入后端的进度接口 URL，带上 taskId 参数，并设置 withcredentials:true 确保Cookie能带过去做身份验证。

消息处理的核心在回调里。每收到一条消息，先提取消息类型前缀，然onmessage后走不同的处理分支。比如收到AGENT3STREAMING 前缀的消息就知道这是正文的流式内容，收到IMAGECOMPLETE就知道有一张图搞定了。

打字机效果的实现原理其实很简单-组件里维护一个fullcontent字符串变量，每次 onmessage触发时，把新收到的文本片段追加到这个变量末尾。由于Vue的响应式系统，变量一变，页面就会自动重新渲染，用户就看到内容一点点冒出来。为了增强视觉效果，在内容末尾还显示了一个闪烁的| 光标，创作完成后自动隐藏。

还做了自动滚动:每次内容更新后，用scrollToBottom()方法把容器滚到底部，确保用户始终能看到最新生成的内容，不用手动往下翻。
流结束时，后端会发送一个ALLcoMPLETE类型的消息。前端监听到这个事件后调用eventSource.close()关闭连接，然后触发文章的加载和展示。错误处理上，onerror里会做断线重连或提示用户。

AI爆款文章创作器项目中大纲流式输出时，怎么解析不完整的JSON?

这是一个比较有意思的前端处理场景。大纲是以JSON格式流式返回的，但在流式传输过程中，前端每次拿到的只是JSON的一个片段，比如("sections”:[{"title”:"第一章"，"po，这时候直接JSON.parse()肯定会报错。

我的解决方案是在每次收到新的文本片段后，先累积到一个 outlineRaw 变量里，然后尝试解析。如果JsON.parse()成功了，说明拿到了完整的JSON，直接用。如果报错了，就尝试做一些修补-找到最后一个完整的}括号的位置，截取到那里，手动补上缺失的闭合括号和方括号，再尝试解析。

具体来说就是:在累积的文本里从后往前找到最后一个}，截取到那个位置，然后检查还缺多少闭合符号( ] 和 } )，补上之后尝试解析。这样即使JSON还没传完，也能提取出已经完成的部分章节，实时展示给用户。

这个parsedoutline 做成了Vue的计算属性，每次 outlineRaw 变化时自动重新计算。用户能看到大纲一个章节一个章节地冒出来，而不是等全部传完才一次性显示。虽然中间可能有片刻展示不出最新的那个还没写完的章节，但整体效果比干等强很多。

### 项目中拖拽排序编辑大纲是怎么实现的?

大纲编辑阶段用户可以直接拖动章节来调整顺序，这个功能用的是SortableJS库。

实现上，大纲列表渲染为一组可拖拽的卡片。在组件挂载时，用Sortable.create()初始化拖拽功能，绑定到列表的DOM容器上。SortableJS会自动处理拖拽的视觉反馈(元素跟随鼠标移动、占位符提示插入位置等)，拖拽结束后触发onEnd回调。

在回调里，我根据SortableJS提供的 oldIndex 和newIndex，对Vue响应式数组里的大纲数据做相应的重新排序。因为直接操作的是响应式数据，页面会自动更新。

除了拖拽排序，大纲编辑还支持手动添加新章节(在末尾追加一个空章节对象)和删除章节(从数组中移除)。每个章节的标题和要点都是可编辑的输入框，用v-model双向绑定到对应的数据字段上。用户编辑完后点确认，前端会把整个大纲数据发给后端，后端更新到数据库里。

这里用到了Vue的Transition组件做列表的过渡动画(fade-slide)，章节的增删和排序变化都有平滑的动画效果，用户体验上比生硬的切换好很多。

### 项目中 Markdown 渲染和代码高亮是怎么实现的?

AI生成的正文是Markdown格式的，需要渲染成HTML展示给用户。我用了marked 库来做Markdown解析，配合highlight.js 实现代码块的语法高亮。

封装了一个markdownToHtml()工具函数，内部调用marked.parse()把 Markdown字符串转成HTML。在marked的配置里集成了 highlight.js，这样遇到代码块时会自动检测语言并添加高亮样式。

在组件里用v-html指令把转换后的HTML渲染到页面上。由于正文是流式输出的，markdownToHtml()会在每次内容更新时被调用，实现实时渲染。

有个细节需要注意:流式输出过程中，Markdown的结构可能是不完整的，比如一个代码块的开头 已经出来了但还没到闭合的 。 marked对不完整的Markdown有一定的容错能力，大部分情况下不会出问题。偶尔出现渲染异常也是瞬时的，等后续内容补齐后就正常了。

文章详情页展示的是最终完成的Markdown，不存在不完整的问题，渲染效果比较稳定。

### 项目中三阶段的前端状态管理是怎么做的?

创作页面需要在三个阶段之间平滑切换:标题选择、大纲编辑、正文生成。每个阶段的UI完全不同，状态数据也不一样。

我用了多个Vue响应式变量来管理:currentPhase 标记当前所处的阶段，isCreating标记是否在创作中，isStreaming标记是否正在接收流式数据，isCompleted标记创作是否完成。这些变量组合起来就能驱动整个页面的状态切换。

阶段切换的触发来自SSE消息。收到TITLESGENERATED 时，把标题方案存到titleoptions变量里，currentPhase切到标题选择;用户确认后调接口，接口成功后currentPhase切到大纲阶段等待;收到oUTLINE GENERATED 时切到大纲编辑界面。

页面模板里用v-if/v-show 根据currentPhase 的值来控制显示哪一块Ul。为了切换更平滑，用了Vue的<Transition>组件加上fade-slide 动画，阶段切换时有一个淡入淡出的效果。

各阶段的数据彼此独立:标题阶段用titleoptions 和selectedTitle，大纲阶段用outlineRaw 和 parsedoutline，正文阶段用fullContent 和 article。 确认操作的按钮会根据当前阶段的状态来控制可用性，避免重复提交。

还有一个细节是进度步骤条。页面顶部有一个Ant Design的Steps组件，展示创作的6个步骤(生成标题、规划大纲、撰写正文、分析配图、生成配图、图文合成)，currentStep变量跟随智能体的执行进度更新，给用户一个清晰的整体进度感知。

### 项目中前端路由是怎么设计的?权限控制在前端怎么做?

路由用Vue Router集中配置，主要的页面有创作页(/create)、文章列表页(/article/list)、文章详情页(/article/:taskId)、VIP购买页(/vip)以及管理员的统计页(/admin/statistics)。部分页面用了路由懒加载(()=>import(...))来优化首屏加载速度。

前端权限控制做了两层。第一层是路由守卫，在router.beforeEach 里拦截。每次路由跳转前，先从Pinia的useLoginUserStore 里拿到当前用户信息。如果目标路径以/admin开头，就检查用户角色是否是admin;如果需要登录的页面而用户未登录，就跳转到登录页。

第二层是UI层面的菜单隐藏。在全局导航栏GlobalHeader组件里，菜单项会根据用户角色动态过滤。普通用户根本看不到管理员入口，非VIP用户也看不到某些VIP专属的操作按钮。

需要强调的是，前端的权限控制只是体验层面的优化，真正的安全保障在后端。后端的@Authcheck 注解会做最终的权限校验，即使前端被绕过了，后端也能拦住非法请求。

### 从前端性能优化角度，项目有哪些可以改进的地方?

第一个是流式渲染的性能。目前每收到一个Token就更新响应式变量，触发一次Vue的重新渲染。如果Token推送得很快，短时间内可能触发几十上百次渲染。可以考虑做一个节流处理，比如每50毫秒才合并更新一次，减少不必要的DOM操作。

第二个是Markdown渲染优化。每次内容变化都重新解析整段Markdown，其实只有末尾新增的部分是需要处理的。可以考虑增量渲染--只对新增的文本做解析，然后追加到已有的HTML后面，避免重复解析大段已有内容。

第三个是大文件的内存占用。一篇长文章的Markdown源码加上渲染后的HTML，可能占用不少内存。如果用户在一次会话里创作了多篇文章而没刷新页面，内存会持续增长。可以在页面切换时及时清理不需要的状态数据。

第四个是静态资源优化。可以配置更长的浏览器缓存策略，以及把前端打包产物部署到CDN上，减少加载延迟。

第五个是SSE断线重连。目前如果网络抖动导致SSE连接断开，需要用户手动刷新。可以在 onerror回调里实现自动重连机制，维护一个已接收内容的位置标记，重连后从断点继续。


### 项目是怎么部署上线的?完整流程是什么?

整个部署分为环境准备、后端部署、前端部署、Nginx配置四个步骤。

环境准备阶段，我在一台Linux服务器上安装了宝塔面板来做服务器管理，然后通过面板安装了MySQL 8.x、Redis、Nginx。另外还手动安装了JDK 21和Node.js 作为运行环境。数据库建好库、导入建表SQL、创建用户授权。

后端部署方面，在本地项目里创建application-prod.yml配置文件，把数据库连接、Redis地址、各个API Key、COS配置等生产环境参数填进去。然后用Maven打包成可执行JAR，上传到服务器，用nohup java -Xms512M -Xmx1024M -jarxxx.jar--spring.profiles.active=prod & 后台启动。生产环境还关闭了 MyBatis 的 SQL 日志、给Knife4j接口文档加了密码保护。

前端部署方面，在.env.production 里把API地址配成相对路径(这样走Nginx反向代理就不会有跨域问题)，然后 npm run build打包成dist 目录，上传到服务器上Nginx托管的位置。

最后是Nginx配置，这是把前后端串起来的关键环节。Nginx监听80端口，前端请求走默认的1ocation/，配上 try_files 处理单页应用的路由。后端API请求走location/api，通过 proxy_pass转发到后端的8123端口。SSE接口需要特殊配置，下面单独说。

### 项目中Nginx承担了哪些职责?SSE场景下需要做什么特殊配置?

Nginx在项目中承担三个主要职责。

第一是静态资源托管，把Vue前端的打包产物放在Nginx的 root 目录下，所有前端页面请求都由Nginx直接返回。配合 try_files $uri $uri/index.html/index.html规则来处理单页应用的前端路由，避免用户刷新页面时出现404。

第二是反向代理，把所有/api开头的请求转发到后端的SpringBoot应用。这样前后端共用同一个域名和端口，从根本上解决了跨域问题，也隐藏了后端服务的真实地址。

第三是针对SSE长连接的特殊处理，这是最容易踩坑的地方。Nginx默认会缓冲后端的响应，也就是攒够一定量的数据再一次性发给客户端。对于SSE来说这是灾难性的用户明明在等实时推送，结果Nginx把数据攒在那不发。所以我在/api/article这个SSE接口的location里专门做了配置:proxy_buffering off 关掉响应缓冲，proxy cache off 关掉缓存，proxy read timeout 86400s 把读超时设成24小时防止长时间没有数据传输时Nginx主动断开连接)，chunked_transfer_encoding on确保分块传输。同时开启了 tcp_nopush和tcp_nodelay来减少网络延迟。

如果不做这些配置，SSE的表现会非常诡异--要么数据一大块一大块地跳出来而不是逐字显示，要么连接莫名其妙断开。

### 项目中从哪些方面对系统做了优化?举个例子详细说说?

系统优化主要涵盖了性能、用户体验、可用性和成本这几个方面。

性能方面，最核心的优化是配图生成的并行化。原来5张图串行生成要20多秒，改成按图片来源分组并行后缩短到5-8秒。另外异步任务用了自定义线程池替代默认的SimpleAsyncTaskExecutor，避免了线程无限制创建的风险。统计数据的Redis缓存也减少了数据库的压力。

用户体验方面，最大的提升就是HumanintheLoop的三阶段设计。用户不再是把选题扔进去干等结果，而是能在标题和大纲阶段参与决策，让最终文章更符合预期。另外SSE流式推送的打字机效果也比传统的加载转圈好很多。

可用性方面，配图服务的自动降级机制保证了即使某个外部API挂了，文章创作也能完整走完。AOP自动记录的智能体日志也方便了问题排查。

详细说说并行优化这个例子。在 ParallelImageGenerator 里，我先根据imageSource字段把配图需求列表分组。假设有5张图，2张来自Pexels、2张来自Nano Banana、1 张来自Mermaid，那就分成3组。然后对每组创建一个 completableFuture.supplyAsync()，3组同时开始执行。每组内部按顺序一张张处理，避免对同一个API的并发过高。最后用CompletableFuture.al10f().join()等所有组完成，再把结果汇总。实测这种方案下，5张图的总耗时基本等于最慢那一组的耗时，比串行快了3-4倍。

### 项目Docker部署方案是怎么设计的?

除了传统的宝塔面板部署方式，项目还提供了Docker Compose一键部署方案，适合想要快速搭建环境的场景。

Docker Compose 文件里定义了几个核心服务:MySQL、Redis 和后端应用。MySQL和Redis用的官方镜像，通过环境变量配置初始密码和数据库。后端应用通过Dockerfile打包-基于JDK21的基础镜像，把JAR包复制进去，配置启动命令和JVM参数。

各服务之间通过Docker网络通信，后端配置里的数据库和Redis地址直接用容器名比如mysql:3306)，Docker会自动做DNS解析。数据持久化用volume挂载，确保容器重启后数据不丢。

部署的时候一条命令就行:dockercomposeup -d --build。它会自动拉镜像、构建应用镜像、启动所有服务并处理好依赖顺序。前端的Nginx同样可以容器化，或者直接在宿主机上跑也行。

这种方案的优势是环境隔离和可复现-不管在什么服务器上，只要装了Docker，同一份Compose文件就能跑出一模一样的环境。也方便做开发和测试环境的快速搭建。

### 你觉得项目中最有技术挑战的功能是什么?

我觉得最有挑战的是多配图方式的扩展+占位符精确合成这一整套方案的设计。

挑战在于要同时解决好几个问题:6种配图方式各有不同的接入协议和数据格式，需要统一封装;AI生成的占位符位置需要精确且不能跟正文内容冲突;封面图和正文配图的处理逻辑不同，封面图不应该出现在正文里;不同来源的配图需要并行获取以优化性能;还要有可靠的降级机制保证任何一种配图服务挂了都不影响整体。

解决过程中做了几个关键的设计决策。首先是策略模式解决了多种配图方式的扩展性问题，ImageServiceStrategy 的自动注册机制让加新配图方式变得很简单。然后是ImageData统一封装解决了数据格式差异的问题。占位符方案则是从最初的"遇到标题就插图"逐步演进到支持两种占位符格式(普通图片和行内图标)，并且把封面图从正文中独立出来单独存储。

中间踩了不少坑。比如最开始封面图是插在正文开头的，后来发现前端需要在文章列表卡片上单独展示封面图，如果封面图只存在正文里就没法灵活使用了，所以才重构为独立的 coverImage字段。还有Mermaid渲染一开始想用纯Java库实现，后来发现效果不好，才改成调mermaid-cli命令行工具，虽然多了个Node.js的依赖但渲染效果好很多。

这个功能最终的实现效果我觉得还是不错的-既保证了架构的可扩展性，又兼顾了性能和可用性，是整个项目里设计最花心思的部分。

### 你是怎么看AI辅助编程的?在项目中用得多吗?

我在这个项目中大量使用了AI辅助编程，总体感受是它确实能大幅提升效率，特别是在一些模式化的工作上。

比如项目初始化阶段的前后端脚手架搭建、用户模块的CRUD接口、前端的通用布局和路由配置，这些重复性高的工作交给AI写，几分钟就能出来一个能跑的版本，自己再微调一下就行了。ECharts图表的配置代码也是AI生成的，手写那些配置项太痛苦了。

但也遇到了不少需要注意的地方。AI生成的代码不能盲目信任，需要仔细审查。比如SSE连接的地址配置、前端Long类型的精度丢失问题，都是AI代码里潜藏的bug，得有足够的经验才能发现。对于核心的架构设计(比如策略模式怎么组织、状态机怎么设计、StateGraph怎么编排)，AI可以给出方案参考，但最终的决策还是得靠开发者自己基于对业务的理解来做

总结来说，AI辅助编程把开发者从"写代码的人"变成了"指挥AI写代码的人"。对Prompt质量的要求、对生成代码的审查能力、对架构的把控能力变得更重要了。它不是替代编程能力，而是放大编程能力。
